## Agent loop / 上下文压缩 / 决策模式

- **Agent loop 抖动恢复体系**（`admAgent/internal/agent/agent_loop_llm.go`）：空 stop 重试（上限 3）、叙述性 stop 重试、推理超限（软阈值统一 `reasoningOverrunMaxTokens` = 120000 **估算 token**，**不再按 reasoning_effort 分档**；估算规则 ASCII ≈4 字节/token、非 ASCII rune 计 1 token，见 `outputDegradationDetector.tokens`；超限或 max_tokens 被推理吃光时丢弃+nudge，上限 2 次）、未完成 todos nudge（**进度感知**：连续 3 次无进展才放弃，有进展（todo 完成或 edit/write/bash 等实质副作用工具成功）即清零计数，硬熔断总上限 10 次）、假完成检测。每次「丢弃半成品并重试」前先推一条 `agent_event type=thinking`（`progress` 为稳定 token：`discard_reasoning_overrun` / `discard_stream_interrupted`，见 `notifyDiscard`；桌面端 `DISCARD_NOTICE_TEXT` 额外保留已不再发出的 `discard_reasoning_timeout` 一个版本周期，防止旧 sidecar 的提示退化成英文 token 原文），桌面端 `sse.js` 按 token 提示“思考被丢弃并重新生成”（旧版服务端无该事件时按被删消息内容兜底）——否则用户只看到思考气泡凭空消失（表现为“思考很久 → 突然清屏 → 又继续思考”）；TUI 忽略 thinking 通知（`internal/ui/model/ui.go` 的 default 分支）不受影响。重试耗尽后本轮**无 error 静默结束**（run_complete 不带错误），UI 侧表现为“突然停了”。
- **空正文提示 + empty_output**：step 流式输出只有 reasoning、无正文/工具调用时，每 60s 推一次 `agent_event type=thinking`（progress 带已思考秒数，前端 `showInfo` 提示“模型仍在思考…”）。这是**纯提示、不打断**：思考时长不设上限（原 `emptyTextNudgeAfter` 300s 看门狗已删除），单步只有 `reasoningOverrunMaxTokens` 这个 token 预算在约束。本轮正常结束但无任何输出（正文与工具调用皆无，或 assistant 消息被丢弃）时 `run_complete` 携带 `empty_output: true`，前端提示“模型未产生有效输出”且不自动续跑。
- **压缩摘要的确定性事实块**（服务端 `internal/context/facts.go`）：每次压缩在摘要前缀（`---` 围栏内、Rail 0 anchor 之后）追加一段**代码抽取、模型不参与**的 `[Session Facts]`：`Modified`（`edit/multiedit/lsp_replace_symbol` 的 `file_path`）、`Created`（`write`）、`Commits`（bash 的 `git commit -m` 主题 + 紧随 tool_result 里的短 hash）、`Archived`（归档编号区间 + `range/expand` 用法提示）；`Read` 段默认关（`options.fact_block_read` 打开后由 `filetracker.ListReadFiles` 注入，**不要**改用 filetracker 的写记录——它是内存态 + 10 分钟 TTL）。整块 600 字符上限、每类 10 条 + `(+N more)`、路径裁到最长公共目录前缀；总开关 `options.fact_block`（默认 true，nil=开）。生命周期与 anchor 块完全对齐：`CompactWithBudget` 从上一版摘要 `MergeFromText` 解析回来 → `StripFactBlock` 剥掉后才归档 → 下次重新渲染，故不会重复累积；**`carryForwardSummaries` 必须同时剥 anchor 与 fact 两个块**（漏一处每轮叠一层）。
- **归档编号 `#N` 的三条不变量**（摘要/事实块里的 `(#1253)` 与 `recall` 同构）：① 编号 = 会话内消息序号（`messages.List` 的 `created_at, rowid` 顺序，`getSessionMessagesWithIndex` 产出 map），归档条目用现成的 `Entry.Turn` 承载，**不必加新列**；② 已归档条目永不被删除（撤销/丢弃只删活动上下文尾部），归档时编号被占用则顺延 `max+1`（`claimTurn`），保证 `#N → 条目` 唯一可解；③ 升级后**首次压缩该会话时必须 `BackfillTurns` 回填**旧条目的局部编号（映射不到的消息置 `-1` = 不可寻址），漏做会让 `expand:[N]` 静默返回错误条目。`recall` 工具新增 `range:[a,b]`（20 条/页）、`expand:[N]`（≤5 条，单条 `recallRefEntryTokens`=1200 token、总预算 2000 token；工具描述写的是"capped at ~1200 tokens each"，不要再写成 FULL untruncated）与"未用参数点名 / 越界明说 / 下一步提示"；取回走 `Store.LoadByTurns`（无 store 时用内存 `memEntries`）。被动 `RecallStrict` 注入路径未改。方案与实施记录见 `doc/admAgent-fact-block-and-recall-refs-plan.md`。
- **上下文窗口下限与压缩经济性（服务端 `internal/agent/agent.go`）**：设计目标是 **≥128k 窗口**（`recommendedContextWindow`）。判定式：`可用工作窗口 = guard(cw) − 固定开销 − 2×摘要上限`，要求 ≥ `minUsableWorkWindow`(25k)；实测 28 工具时固定开销 ≈ 22.9k（系统提示/前缀/项目记忆 16.4k + 工具 schema 6.5k，每工具 ≈ 232 token）。64k 窗口下可用窗口只剩 ~10.7k（**每 4 步就要压缩一次**，每次 15–70s，本地模型实测占墙钟 ~25%），32k 下固定开销直接超过 guard（压缩永远落不了地）。低于该线时 `Summarize` 会打 `context window leaves a small work window` 警告（带 work_window_tokens/fixed_overhead/advice），提示改窗口或精简工具目录/系统提示。**caps 按 128k 分档**：`deriveSummaryMaxTokens` 3072→6144、`deriveToolResultMaxTokens` 2000→3000（低于 128k 逐字节保持旧行为），给大窗口更多"留在上下文里的事实"（不依赖模型主动 recall 的准确性）；`deriveToolResultCompressThreshold` 保持 6% 但**下限 2000、上限 12000**（`toolResultCompressThresholdCap`）——下限确保高于 `recallToolTokenBudget`（召回结果不被二次压缩），上限防止 6% 在大窗口上失守（1M 窗口下 6% = 60k，实测一条 25.6k token 的 fetch 结果原样进了上下文）。**分档点是 128000 而不是 128KiB（131072）**：厂商标称 128k 的模型配的就是 128000，写 131072 会把最常见的 128k 窗口恰好排除在小档（实测日志 cw=128000 → guard 89600 仍走 3072 小档，也不打 shortfall 警告）。
- **压缩节奏三原则（本地模型实测驱动，改这几处前先读 `doc/admAgent-fact-block-and-recall-refs-plan.md` §7）**：① `maxSummarizeResumes` 是**连续无进展**上限（`nextSummarizeResume`：跑满 `compactionProgressSteps`(3) 步才撞 guard = 有进展 → 计数重置为 1），长任务可以压缩任意多次，熔断时返回明确错误而不是空 error 静默收尾；② 压缩目标水位是 guard 用量的 `compactionHeadroomRatio`(0.85)（`compactionTargetBudget`，clamp 与 tail budget 同步），**且尾部预算自己也要留工作窗口**（`recentTailBudget` 用 `reservedWorkWindow = min(25k, usable/2)` 封顶）——否则尾部能长到落点贴着 guard：实测日志保留尾部 1.9k→4.7k→7.2k→16.6k、落地水位 19k→22k→27k→36k、间隔 18m→14m；③ 超大工具输出**必须在入口就被压掉**（阈值 6% 且上限 12k + `truncateToolOutputDeterministically` 兜底），否则单步 +12k token 会吃掉整个工作窗口。
- **Rail 3 归档投影（服务端 `internal/context/archive_text.go`）**：归档条目不再是 `msg.Content().Text`。工具消息的正文只存在于 `ToolResult` part、工具调用参数只存在于 `ToolCall.Input`，旧实现两者都拿不到，于是**工具输出与 edit/view/grep 细节从未进过 rail3.db**（`recall` 只能召回叙述文本；`#N` 区间因此大量空洞）。现在 `ArchiveText` 按角色投影：Tool → `[tool result <name> (error)]` + 正文（二进制只留占位说明）；Assistant → 正文 + `[tool call <name>] <单行化后的参数>`（每调用 1200 token 上限）；User → 原样。整条上限 `maxArchiveEntryTokens`=4000，超出追加 `[archived entry truncated…]`（全文仍在 `admAgent.db`）。摘要消息仍由 `CompactWithBudget` 单独处理（剥 anchor/facts 后归档），`ArchiveText` 对摘要返回空。**新增归档来源时必须复用这个投影**，否则又会出现"某些 part 永远不可召回"。`clampContextUnderLimit` 丢弃保留尾部的旧消息前也先走 `Manager.ArchiveOriginal`（`Turn=-1`），避免"被 clamp 掉 = 永久丢失"。
- **统一 token 估算器（`internal/tokencount`）**：压缩预算与发送守卫必须用同一套估算，否则会出现"预算说没超、provider 说超"。规则：ASCII 字节 /4（与旧行为逐字节一致），**非 ASCII rune 计 1 token**（中文实测 ≈1–1.5 token/字；旧的 `context.approxTokens` 用 rune/4、`AnchorStore.CompactToBudget` 用字节/4，把中文预算放宽了 3–4 倍）。接入点：`agent.approxTokenCount`、`context.approxTokens`、`truncateRunesToTokens`、`truncateToTokens*`、`clipMiddleToTokens`、`AnchorStore.CompactToBudget`。另新增 `messageTokenCount`（正文 + reasoning + **全部 ToolResult 正文** + **ToolCall.Input** + 内联文本附件）替换所有"只数 Content().Text"的预算点（尾部预算、压缩前后计数、clamp 扣减、摘要档位比例）——旧算法看不到工具结果/工具参数/文本附件，保留尾部可以远超预算而守卫以为还有空间。
- **超大保留消息定点截断（`truncateOversizedKeptMessages`，`agent.go`）**：压缩后若仍高于落点水位（`compactionTargetBudget`），先找出**单条**超过 `outlierMessageTokens = max(落点/4, 2×工具结果上限)` 的保留消息，对正文/推理/工具结果做确定性截断（`clipMiddleToTokens` / `truncateToolOutputDeterministically`），截断前把原文写进 Rail 3（`Manager.ArchiveOriginal`，`Turn=-1`、不可 `#N` 寻址但可 `query`），然后 `messages.Update` 落库并重算 token。它替代"对一个超大输出再跑两档 LLM 压缩"：摘要替换的是旧历史，而这条消息在保留尾部，重压一次也不会变小。命中时打 `Agent: truncated an oversized message kept verbatim instead of re-compacting`（带 before/after/threshold/target）。摘要消息、user 消息（含任务目标）永不重写；一旦落到目标水位即停止。
- **压缩冷却的跳过语义（`errSummarizeSkipped`）**：`Summarize` 在 30s 冷却内不再返回 `nil`，而是返回哨兵错误；`Run` 识别后等完剩余冷却（`waitSummarizeCooldown`，最多一个窗口、可取消）再重排队，并且**不消耗** `maxSummarizeResumes` 配额——旧行为会把"一次都没压"当成"压缩无效"，4 次后以 `context compaction is no longer buying usable work time` 结束本轮。手动 `/summarize` 在 `coordinator.Summarize` 把该哨兵映射为成功（冷却期内重复点击是 no-op，不报 500）。日志：`summarize skipped, a compaction just ran for this session`（带 remaining）与 `waiting out the summarize cooldown before retrying compaction`。
- **facts 抽取范围 + 活摘要去重**：`Manager.MergeFacts(sessionID, msgs)` 在 `CompactWithBudget` **之前**用整个工作上下文抽 facts（旧实现只抽待压缩区间，留在尾部或随后被 clamp 丢弃的编辑/提交永远不会进 `[Session Facts]`；`MergeFromMessages` 幂等，重复扫描无副作用）。召回去重靠 `SetLiveSummary`：`sessionMessages` 每次加载/压缩后把当前摘要文本登记到 Manager，`Recall`/`RecallRanked`（含严格路径）会丢掉"文案长度 ≥40 且被活摘要包含"的条目，避免把模型已经看到的决策再注入一遍；`RecallByRange`/`RecallByIndex` 不受影响（显式 `#N` 必须精确返回）。`DeleteSession` 会清掉该登记。
- **压缩落点校准 / 假压缩 / 恢复续跑 / 尾部边界（真实请求回归，2026-10-21）**：四处改动集中在 `agent.go` 与 `agent_loop_llm.go`。① **落点估算校准**：每步拿"provider 实测 `prompt_tokens` ÷ 锚定前的启发式估算"学偏差（`recordEstimateScale`：仅 >1.02 记录、与旧值取均值、上限 `maxEstimateScale`=1.6），`estimatePostSummarizePromptTokens(sessionID, …)` 按会话缩放；摘要日志新增 `estimate_scale`——实测 40k 窗口压缩后 est 19567 vs 实测 23150（落在 guard 93%，只剩 1650 token，日志却报工作窗口 6420），修正后落点不再贴边。② **假压缩**：`compressionReduces` + `toolCompressionMinGainPct`=90，抽象结果没缩到原 90% 以下即按失败返回，走 `truncateToolOutputDeterministically`；**收益判定必须在调用方也做一次**——单行 dump 没有 middle 可抽象，`compressToolResult` 会原样返回，之前正是这条路径打出 `[compressed tool output, ~3012→3012 tokens]`（实测改为 `~3012→1207 tokens` 的确定性截断）；③ **恢复续跑**：`call.summarizeResumes > 0` × 本轮尚未用过工具 × 回复是短句（≤60 字符且无换行）时，`resumeContinuationNudge` 推一次继续（每轮最多 1 次），不再走"非编码任务叙述性回答结束"分支（实测 6 轮任务在压缩后只回 "OK" 就结束了整轮）；④ **尾部边界**：`alignTailBoundary` 把保留尾部起点回退到所属 user 消息（最多回看 `tailBoundaryScanLimit`=8 条，且不越过 `startCompress`），避免 wire 上出现 summary(assistant) 紧跟 assistant(tool_call) 的孤儿步骤。单测见 `internal/agent/compaction_resume_test.go`。
- **配置词表统一（admAgent 侧；桌面端下轮跟进）**：模型条目只有三个词 —— `ctx_size`（窗口，取代 `context_window`）、`output_tokens`（输出上限，取代 `default_max_tokens`；**不填则派生** `ctx_size − max_summarize_tokens`，再被 provider 硬上限 `provider_max_output_tokens`（池 JSON 仍写 `max_output_tokens`）夹住）、`options.max_summarize_tokens`（压缩阈值，按**整个请求**的 committed token 计：系统提示 + 工具 schema + 历史 + 召回；`0` = 沿用旧的比例规则 62%(≤64k)/70%）。旧名全部保留为别名（`ModelInfo.UnmarshalJSON` / 池 `BackendModel.UnmarshalJSON`），所以现有 admAgent.json 与仍写旧名的桌面端不受影响；wire 上的 `max_tokens` 是协议字段，不改。阈值只能让压缩**更早**：`sizingContext` 把阈值反解成等效窗口，让 target/tail/keep/各类 caps 跟着走（高于窗口自身 guard 的值被夹到窗口上限），`summarizeLimit` 供 pre-send guard、压缩闭包检查与决策轮使用。**桌面端（`src-tauri/src/pages/agent.rs`）同步跟进**：写 admAgent.json 时**双写**新键与旧键（本地模型同步、新增/修改 provider 三处），读时新键优先、旧键兜底——这样"新桌面 + 只认旧键的旧 sidecar / 仍在跑的旧 server 进程"仍能读到窗口与输出上限；schema.json 里三个旧键以 `Deprecated:` 形式保留，旧键配置也能通过校验。等旧版本退出支持窗口后再删旧键与双写。
- **决策输出模式（服务端，可选）**：`POST /v1/workspaces/{id}/agent` 可带 `decision: {mode: auto|choice|bool|score, tool_policy: none, structured_output: auto|off}`（`proto.DecisionSpec` → `agent.WithDecisionSpec(ctx)` → `SessionAgentCall.Decision`）。带该字段的轮次走**独立旁路** `internal/agent/decision_turn.go`：契约系统提示词由 `internal/decision` 注入（不进用户消息/历史/标题），不注册工具、不进主循环的 nudge/看门狗，单次请求 + 失败一次定向重试；`structured_output=auto` 时附带 `response_format` json_schema（`internal/llm` 探针：被拒即不带该字段重试一次并按 `baseURL+model` 缓存）。校验通过的结果写入**专用 ContentPart** `{"type":"decision","data":{kind,mode,reason,selected,candidates,value,score,min,max,level,raw}}` 并把正文里的 JSON 剔除（`message.DecisionContent` / `SetDecisionResult`；part 插在 finish 之前）；**新增 part 类型必须同时登记四处**：`internal/message`（存储 `partType`）、`internal/proto/message.go`（wire 白名单 + MarshalParts/UnmarshalParts）、`internal/server/events.go` 的 `messageToProto`（SSE 与 `/messages` 共用）、`internal/workspace/client_workspace.go` 的 `protoToMessage`（客户端模式 proto→message，漏登记会静默丢弃）——前者漏登记表现为"服务端成功但前端拿不到 part"，另两处漏登记表现为 TUI/`adm session show` 看到空消息或 `unknown` part；`internal/cmd/session.go` 的 `convertParts` 决定终端展示；两次校验不过则 `run_complete.error = invalid decision output…`。分派点 `internal/agent/agent.go:1090` 的 4 行 if/else，`agent_loop_llm.go` **零改动**；省略字段 = 普通对话，TUI 忽略未知 part 不受影响。桌面端只发字段并优先按 part 画卡片（`src/views/agent/decision_mode.js`、`render.js`），决策轮不走折叠插入（强制排队）。决策轮**在服务端强制关闭...

- **MCP 工具的 JSON Schema 原样发出，不能"从 properties 重建"**：发给模型的工具定义由 `buildLLMTools`（`admAgent/internal/agent/agent_loop_llm.go`）产出。内置工具（反射生成）仍由 `{"type":"object","properties":…,"required":…}` 拼装，但 MCP 工具带的是服务端自己的完整 schema（`Tool.Info()` → `ToolInfo.Schema`，`internal/llm/agent/tool.go`），必须**逐字发出**：只取 `properties`/`required` 会丢掉所有同级关键字，后果分两类——① `$defs`（draft-07 是 `definitions`）被丢，属性里的 `$ref` 悬空，严格上游**在生成前**整包 400：`Invalid schema for function 'mcp_x_y': Pointer '/$defs/__schema2' does not exist`；② 根级 `$ref`/`allOf`/`anyOf`（pydantic `RootModel[Union[…]]`、zod `.and()`/`union` 都会生成）被丢，`properties` 取空，工具被当成"无参数工具"，调用必然缺参。用户侧表现为「发出后秒失败、重试报错一字不差」，或「工具永远缺参数」，而同一模型在没有该 MCP 的工作区完全正常（排查先确认是否只在特定工作区复现）。实现要点：`internal/agent/tools/mcp-tools.go` 的 `toolSchema()` 只在"根级引用/组合关键字解析后确属 object"时返回原文档（顺带补 `type:"object"`，**浅拷贝**、不改动服务端缓存的 schema），否则返回 nil 让 `buildLLMTools` 走老的重建路径；`isObjectSchema()` 判定 object 形状，`resolveTopLevelRef`/`lookupLocalRef` 负责根级 `$ref` 跟随（8 跳上限、带环检测）。回归用 `internal/agent/tools/mcp_tools_test.go` 与 `internal/agent/tools_schema_wire_test.go`——两者都断言发出的 schema 里每个本地 `$ref` 都能解到，且 `additionalProperties`/组合关键字不丢。

## 网络代理链路

- **网络代理链路**（设置→网络代理，仅影响 admAgent，桌面端下载不走代理）：
  1. 前端 `settings.js` `saveProxy()` 校验（启用时 url 必填、须以 `http(s)://` 或 `socks5://` 开头）→ `save_settings` 写入 config.json 的 `agent_proxy`。
  2. Rust `settings.rs:37` 调用 `agent.rs` `sync_agent_proxy`：`write_agent_proxy`（`agent.rs:640`）把 `{enabled,url}` 写入 admAgent.json 顶层 `agent_proxy`（原子写，值未变返回 false 跳过）→ 有变更时对当前 active workspace `POST /v1/workspaces/{ws}/config/set` 触发服务端**磁盘全量重载**（10s 超时，失败仅记日志退回直连）。
  3. admAgent `ConfigStore.setConfig` 把代理同步到进程级 `httpproxy`（`internal/config/store.go:100-105`）；`httpproxy.ProxyFunc()` 作为 `Transport.Proxy` 回调**每次请求实时读取**状态，热重载即刻生效、无需重建 client/重启 server；本地/私网地址（127.0.0.1、LAN GPU 盒）自动绕过（`internal/httpproxy/proxy.go:50-81`）。
  4. **生效范围**：LLM 客户端（`llm/client.go:107`）+ Agent 网络工具 fetch/web_fetch/download/web_search/sourcegraph/agentic_fetch（全部经 `SharedHTTPTransport`，`tools/fetch_helpers.go:38-48`）；**MCP HTTP/SSE 传输不走**（`mcp/init.go:538-581` 用 `http.DefaultTransport`，只认 `HTTP_PROXY` 环境变量）。注意：面板文案"仅影响 LLM 请求"比实际范围窄，工具类请求同样走代理。
