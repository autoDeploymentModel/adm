# admAgent 服务端约定与调优

> 范围：服务端（Go）行为与前后端契约 —— Agent loop 抖动恢复、上下文压缩与事实块、系统提示词预算与提示词缓存、归档编号、决策输出模式、代理链路、配置词表。改动前先读本文对应小节。

## Agent loop / 上下文压缩 / 决策模式

- **Agent loop 抖动恢复体系**（`admAgent/internal/agent/agent_loop_llm.go`）：空 stop 重试（上限 3）、叙述性 stop 重试、推理超限（软阈值统一 `reasoningOverrunMaxTokens` = 120000 **估算 token**，**不再按 reasoning_effort 分档**；估算规则 ASCII ≈4 字节/token、非 ASCII rune 计 1 token，见 `outputDegradationDetector.tokens`；超限或 max_tokens 被推理吃光时丢弃+nudge，上限 2 次）、未完成 todos nudge（**进度感知**：连续 3 次无进展才放弃，有进展（todo 完成或 edit/write/bash 等实质副作用工具成功）即清零计数，硬熔断总上限 10 次；**文案必须点名 `todos` 工具**——2026-10-28 实测：只列 "read, edit, write, bash, grep" 的泛化文案被弱模型读成"继续用 bash 复检"，93 步里只有 1 次 `todos` 写入，10 次 nudge 全部照旧，面板停在 0/4；`todoNudgeEscalateAfter`=3，从第 3 次起文案升级为"要么用 `todos` 回写完成态、要么继续干活，禁止再输出空泛正文"）、**运行中 todo 状态提醒**（`todoStatusLine` + 两个文案构造器：轮首用 `todoStateReminder`、运行中用 `todoProgressReminder`。轮开始时清单仍有未完成项 → 先发一次；此后每 `todoProgressReminderEvery`(3) 次成功的实质副作用工具调用（`todos` 之外的 edit/multiedit/write/bash/改符号/rename/download）都没换到一次 `todos` 回写 → 再发一次。文案带 `N/M completed (i in progress, p pending)` + 当前项/下一个待办 + "禁止攒到最后批量回写"，点名 `todos` 工具；上限 `maxTodoProgressReminders`(8) 次/轮，`todos` 回写成功即清零计数；列表为空或全完成时静默。**轮首那条必须写成条件式**（"if the current request continues that task … otherwise ignore this reminder"）：旧清单可能属于用户已经换掉的话题，只有模型能判断本次提问是否延续它；改用提问关键词闸门不可行——`isLikelyCodingTask` 只认英文动作词，"继续" 与一句无关中文提问对它完全同形。**只走尾部 wire-only nudge**，不碰系统前缀。存在的理由：模型上下文里唯一的清单信号是它自己早先那次 `todos` 调用，长回合会漂成"最后一次性批量回写"——2026-11-08/09 日志（≥20 步的 40 个 run）里 17 个用到 todos，其中 12 个**恰好 2 次调用**（开头建表 + 倒数 3 步内标完成），`2026-11-09 19:40` 那个 run 只有 step 18 一次、其后 83 步全无，面板整轮停在 0/9）、假完成检测。正常结束（无 error / 未取消）时 `run_complete.incomplete_todos` 携带剩余未完成数（`session.CountIncompleteTodos`），桌面端据此提示"任务清单还有 N 项未完成"，避免终稿宣称完成与面板 0/N 互相矛盾。每次「丢弃半成品并重试」前先推一条 `agent_event type=thinking`（`progress` 为稳定 token：`discard_reasoning_overrun` / `discard_stream_interrupted`，见 `notifyDiscard`；桌面端 `DISCARD_NOTICE_TEXT` 额外保留已不再发出的 `discard_reasoning_timeout` 一个版本周期，防止旧 sidecar 的提示退化成英文 token 原文），桌面端 `sse.js` 按 token 提示“思考被丢弃并重新生成”（旧版服务端无该事件时按被删消息内容兜底）——否则用户只看到思考气泡凭空消失（表现为“思考很久 → 突然清屏 → 又继续思考”）；TUI 忽略 thinking 通知（`internal/ui/model/ui.go` 的 default 分支）不受影响。重试耗尽后本轮**无 error 静默结束**（run_complete 不带错误），UI 侧表现为“突然停了”。
- **空正文提示 + empty_output**：step 流式输出只有 reasoning、无正文/工具调用时，每 60s 推一次 `agent_event type=thinking`（progress 带已思考秒数，前端 `showInfo` 提示“模型仍在思考…”）。这是**纯提示、不打断**：思考时长不设上限（原 `emptyTextNudgeAfter` 300s 看门狗已删除），单步只有 `reasoningOverrunMaxTokens` 这个 token 预算在约束。本轮正常结束但无任何输出（正文与工具调用皆无，或 assistant 消息被丢弃）时 `run_complete` 携带 `empty_output: true`，前端提示“模型未产生有效输出”且不自动续跑。
- **重复工具调用检测对“后台任务等待”豁免**（`admAgent/internal/agent/loop_detection.go`）：`hasRepeatedToolCalls` 按 `tool+input+output` 签名计数，10 步窗口内同一签名出现 >5 次（`loopDetectionMaxRepeats`）即判定卡死并结束本轮。`job_output` 轮询仍在运行的后台 shell 时结果恒为 `Status: running` + 固定提示文案（`agent/tools/job_output.go`），签名天然相同——实测连续 6 次 `wait=true`（每次 30s）就把一轮健康任务在 ~3 分钟处 `ending turn`，本轮无 error 无正文，用户看到的是“对话自己结束了”（2026-11-01 日志 3 次全部此形态）。现在**只含 `job_output` 且结果为 `Status: running` 前缀的步骤不计入签名**（`isPendingJobPoll`，混合步骤仍计数，`Status: completed` 的重复读取仍会被抓）；豁免有界：单轮等待轮询超过 `jobPollWaitMaxSteps`(40，≈20 分钟) 后恢复计数，避免 dev server / watcher 这类永不结束的任务把回合拖到步数触顶。单测见 `internal/agent/loop_detection_test.go`（等待豁免 / 上限 / 完成后重复 / 混合步骤四条）。
- **同步骤工具调用分段并行执行**（`admAgent/internal/agent/agent_loop_llm.go`）：系统提示词（`coder.md.tpl` 的 `<tool_usage>`）一直告诉模型 "Independent calls belong in one message (parallel tools run concurrently)"，模型因此常在一步里发 3–8 个独立 view/grep/glob 调用，但执行端原先逐个串行，步骤延迟 = 各调用之和。现在按**顺序保持的分段**执行：先把整步调用解析成 `resolvedToolCall`（含别名归一），再切成段——`parallelSafeTools`（view/grep/glob/ls/fetch/web_*/sourcegraph/admAgent_info/admAgent_logs/job_output/lsp 只读四件套/read_mcp_resource/list_mcp_resources/recall/agentic_fetch）里的**连续只读段**以 `maxParallelToolCalls`(4) 为界并发（`executeToolCall`，含超大结果的 LLM 压缩也在段内重叠），变更类（edit/multiedit/write/bash/download/agent）与有状态工具（todos/job_kill/lsp_restart/lsp_rename/lsp_replace_symbol）单独串行——**段边界保证顺序语义**：同一步里 edit 之后的 view 仍看到写后内容。不在 `parallelSafeTools` 里的名字（含全部 MCP 工具，名字动态）一律串行。落库、wire 消息、失败计数、`stepRC` 在 join 后按模型原始调用顺序统一处理，与串行路径逐字节一致；permission 弹窗本就由 `requestMu` 串行化，只读段内越界 view 的弹窗只是排队。回归：`internal/agent/parallel_tool_exec_test.go`（只读双调用必须重叠 / 变更调用必须阻塞同步骤后续调用）。
- **bash 显式后台的快速失败探测改轮询**（`admAgent/internal/agent/tools/bash.go`）：`run_in_background=true` 原先固定 `time.Sleep(1s)` 后查一次 `GetOutput`，秒级命令与被禁命令的失败回报都被白白拖满 1 秒；`GetOutput` 本就是非阻塞 select，改为 100ms ticker 轮询、1s 封顶、`done` 即返回——快速命令按实际耗时回报，慢命令行为不变（仍转后台 job）。
- **工具结果压缩调用加超时并关闭 thinking**（`admAgent/internal/agent/agent.go` 的 `compressToolResult`）：该调用原先拿 `genCtx`（无 deadline）同步执行，而 llm client 只有 5 分钟**空闲**超时、无整体请求超时——慢速滴流的 summarizer 可以把整轮卡住很久，兜底的确定性截断却一直在等。现在整个压缩调用被 `toolResultCompressionTimeout`(90s) 包住，超时按失败返回、调用方走 `truncateToolOutputDeterministically`；同时压缩请求固定 `Thinking: disabled`（原先继承会话设置，对一次性摘要纯属浪费延迟与 token）。
- **回合 panic 隔离 + `admAgent-panic.log`**：`SendMessage` 用 `go b.runAgent(...)`（`internal/backend/agent.go`）把回合派发到脱离 HTTP 请求的 goroutine，`net/http` 的 `recoverHandler` 覆盖不到——一次未捕获 panic 会带走整个 server 进程，桌面端表现为“服务异常退出，正在自动重启”且当轮对话凭空消失。现在 `runAgent` 自带 `defer recover()`：`slog.Error` 记一条带 `stack` 的 ERROR，`log.WritePanic("agent.run", …)` 追加到 `%LOCALAPPDATA%\admAgent\cache\admAgent-panic.log`（同目录、只追加、超 8MB 轮转 `.prev`），并通过 `publishRunFailure` 给 RunID 等待方发 errored `run_complete`（已发布过终态则不重复）。`recover()` 抓不到的 fatal（并发 map 写、栈溢出、OOM）由 `log.Setup` 里的 `debug.SetCrashOutput` 写入同一文件；`log.RecoverPanic` 也从原来的“当前目录 timestamped 文件”改为追加到这里。注意 `admAgent.log` 仍在每次启动时截断，崩溃后**不要**只翻它。
- **压缩摘要的确定性事实块**（服务端 `internal/context/facts.go`）：每次压缩在摘要前缀（`---` 围栏内、Rail 0 anchor 之后）追加一段**代码抽取、模型不参与**的 `[Session Facts]`：`Modified`（`edit/multiedit/lsp_replace_symbol` 的 `file_path`）、`Created`（`write`）、`Commits`（bash 的 `git commit -m` 主题 + 紧随 tool_result 里的短 hash）、`Archived`（归档编号区间 + `range/expand` 用法提示）；`Read` 段默认关（`options.fact_block_read` 打开后由 `filetracker.ListReadFiles` 注入，**不要**改用 filetracker 的写记录——它是内存态 + 10 分钟 TTL）。整块 600 字符上限、每类 10 条 + `(+N more)`、路径裁到最长公共目录前缀；总开关 `options.fact_block`（默认 true，nil=开）。生命周期与 anchor 块完全对齐：`CompactWithBudget` 从上一版摘要 `MergeFromText` 解析回来 → `StripFactBlock` 剥掉后才归档 → 下次重新渲染，故不会重复累积；**`carryForwardSummaries` 必须同时剥 anchor 与 fact 两个块**（漏一处每轮叠一层）。
- **归档编号 `#N` 的三条不变量**（摘要/事实块里的 `(#1253)` 与 `recall` 同构）：① 编号 = 会话内消息序号（`messages.List` 的 `created_at, rowid` 顺序，`getSessionMessagesWithIndex` 产出 map），归档条目用现成的 `Entry.Turn` 承载，**不必加新列**；② 已归档条目永不被删除（撤销/丢弃只删活动上下文尾部），归档时编号被占用则顺延 `max+1`（`claimTurn`），保证 `#N → 条目` 唯一可解；③ 升级后**首次压缩该会话时必须 `BackfillTurns` 回填**旧条目的局部编号（映射不到的消息置 `-1` = 不可寻址），漏做会让 `expand:[N]` 静默返回错误条目。`recall` 工具新增 `range:[a,b]`（20 条/页）、`expand:[N]`（≤5 条，单条 `recallRefEntryTokens`=1200 token、总预算 2000 token；工具描述写的是"capped at ~1200 tokens each"，不要再写成 FULL untruncated）与"未用参数点名 / 越界明说 / 下一步提示"；取回走 `Store.LoadByTurns`（无 store 时用内存 `memEntries`）。被动 `RecallStrict` 注入路径未改。方案与实施记录见 `doc/admAgent-fact-block-and-recall-refs-plan.md`。
- **上下文窗口下限与压缩经济性（服务端 `internal/agent/agent.go`）**：设计目标是 **≥128k 窗口**（`recommendedContextWindow`）。判定式：`可用工作窗口 = guard(cw) − 固定开销 − 2×摘要上限`，要求 ≥ `minUsableWorkWindow`(25k)；固定开销在运行时实测（系统提示/前缀/项目记忆 + 工具 schema），不写死常量：2026-11 精简系统提示后，本仓库 27 工具实测 ≈ 14.1k（系统提示 7.2k + 工具 schema 7.0k，每工具 ≈ 259 token），精简前是 ≈ 19.0k；再把 bash 描述里的 git/PR 剧本（5.2k 字符）搬进 `git-commit` skill、工具描述去重、`<project_structure>` 收到 depth 2 之后，默认目录实测 **≈ 9.2k（2026-11，25 工具：系统提示 3.3k + 工具 schema 5.9k，最大单工具 bash 0.9k）**；`prefixBudgetTokens` 随实测从 9200 调到 9400（余量仍只有一个剧本量级，塞回 1.3k 必爆）。64k 窗口下可用窗口约 ~13k（**每 4–5 步就要压缩一次**，每次 15–70s，本地模型实测占墙钟 ~25%），32k 下固定开销直接超过 guard（压缩永远落不了地）。低于该线时 `Summarize` 会打 `context window leaves a small work window` 警告（带 work_window_tokens/fixed_overhead/advice），提示改窗口或精简工具目录/系统提示。**固定前缀有了硬预算**：`prefixBudgetTokens`(9200)、`maxToolPrefixTokens`(1500/tool)、`maxToolCatalogueSize`(32) 三个常量 + `TestPrefixBudget`（`internal/agent/prefix_budget_test.go`，用生产 `buildTools` 与 `prompt.Build` 实测，不烧模型调用）把闸门放进单测；`coordinator.run` 在 `readyWg.Wait()` 后（`warnIfPrefixOverBudget`，`prefixWarnOnce` 只打一次）与每步 `Loop step request` 日志（新增 `tool_tokens` / `sys_tokens`）都能看到前缀涨没涨。**为什么用单测而不是 eval**：前缀是确定性文本，eval 只能看行为翻转，量不出几百字符的浪费；反过来也不该让 eval 判大小——所以 eval 只把 `prefix_tokens` / `tool_count` 当指标记录（见 `doc/admAgent-eval-harness-plan.md`）。**caps 按 128k 分档**：`deriveSummaryMaxTokens` 3072→6144、`deriveToolResultMaxTokens` 2000→3000（低于 128k 逐字节保持旧行为），给大窗口更多"留在上下文里的事实"（不依赖模型主动 recall 的准确性）；`deriveToolResultCompressThreshold` 保持 6% 但**下限 2000、上限 12000**（`toolResultCompressThresholdCap`）——下限确保高于 `recallToolTokenBudget`（召回结果不被二次压缩），上限防止 6% 在大窗口上失守（1M 窗口下 6% = 60k，实测一条 25.6k token 的 fetch 结果原样进了上下文）。**分档点是 128000 而不是 128KiB（131072）**：厂商标称 128k 的模型配的就是 128000，写 131072 会把最常见的 128k 窗口恰好排除在小档（实测日志 cw=128000 → guard 89600 仍走 3072 小档，也不打 shortfall 警告）。
- **系统提示词的分段与去重原则（`admAgent/internal/agent/templates/coder.md.tpl`）**：静态段只有 7 个（`critical_rules` / `communication_style` / `workflow` / `decision_making` / `intent_clarification` / `editing_files` / `code_conventions` / `tool_usage`），之后才是注入段（`env` → `project_structure` → `lsp` → `available_skills` + `skills_usage` → `project_context` → `user_preferences`）。原则：**机械细节只写在工具描述里，系统提示只放跨工具约束**——edit/multiedit 的白空格与匹配规则、bash 的 background/`description` 规则、grep/glob/view 的"何时用/何时别用"都在各自的 `.md` 里，系统提示只保留一次引用；同一条规则不允许在两处出现（旧模板里 `<bash_commands>` 教"用 `&` 起后台"，bash 工具描述却写 "NEVER use `&`"，模型收到的是互相矛盾的指令）。`agent`/`agentic_fetch` 子 agent 用 `task.md.tpl`，只有一条精简的搜索型提示，不要往里堆 coder 的规则。技能激活流程只在（`{{if .AvailSkillXML}}` 包住的）`<skills_usage>` 里写一遍，`critical_rules` 第 12 条只留一句指针——同一套流程写两处迟早漂移。2026-11 精简结果：模板 28,953 B / 7,253 tok → 11,880 B / 2,976 tok（-59%），本仓库整包（系统提示 + 27 工具 schema）19.0k → 14.1k tok。**后续修正（2026-11）**：`<lsp>` 段改为与工具注册同源（`config.LSPToolsEnabled()`：显式 LSP 条目或 `auto_lsp` 默认开启即渲染），修掉“默认配置下模型拿到 8 个 `lsp_*` 工具、edit/view 输出带 `file_diagnostics` / `project_diagnostics`，却没有‘只修自己改的、忽略其他文件’这条策略”的错位；`<env>` 日期改 ISO-8601（`2006-01-02`）；git 仓库探测改用 `git rev-parse --is-inside-work-tree`（工作目录是仓库子目录或 worktree 时不再误报 `no`），git status 在 Go 里截前 20 行而不是 `| head`（head 来自 PATH，Windows 无外部 coreutils 时整段快照会静默消失）；bash 的工具描述列出 Windows 内置命令集并点名 sed/awk/head/tail/wc 常有缺失（改走 `node -e` 或 grep/view 工具）；`task.md.tpl` 写明子 agent 的输出是回给调用方而不是 CLI，并去掉与“给出路径与片段”冲突的“One word answers are best”。模板当前 12,100 B。
- **工作流剧本属于 skill，不属于工具描述**：bash 描述里曾内联 `<git_message_quality>` / `<commit_messages>` / `<git_commits>` / `<pull_requests>` 四段共 5.2k 字符（占该工具描述的 67%），而它们只在用户要求提交/建 PR 时才用得上，却随每一次请求计费，且与内建 skill `git-commit` 大面积重复。现在这四段搬进 `internal/skills/builtin/git-commit/SKILL.md`（提交信息规范、HEREDOC 用法、hook 失败处理、`git show --stat` 验证、列表报告、PR 全流程），bash 描述只留 `<git>`：一句「先 `view` 该 skill」+ 硬禁区（不 push、不改 config、无 `-i`、无空提交、rebase 一律 `-m`）+ **无法静态化的动态署名 trailer**（`attribution.trailer_style` / `model_id` 由模板按配置渲染，skill 是纯 markdown 做不到）。`coder.md.tpl` 的 `critical_rules` 第 5 条同步改成指针。**判断新增内容该放哪里的标准**：只在少数轮次用到的流程 → skill；每次请求都必须遵守的机械约束 → 工具描述。
- **`<project_structure>` 按深度预算注入**（`internal/agent/prompt/prompt.go`）：`fsext.BuildProjectTree(workingDir, depth, 200)` 的 depth 由 `options.project_tree_depth` 决定（默认 2，夹在 1–8；`0` 取默认）——旧值 depth 4 / 600 文件会把整棵仓库树塞进每一次请求。默认收浅的代价是深层文件要多花 1–2 步 `ls`/`glob`/`grep`，收益是常数级前缀成本不随仓库变大。回归：`TestCoderPromptContainsProjectTree`（默认深度必须看不到 `internal/x/foo.go`，`project_tree_depth=4` 时必须看得到）。

- **MCP 工具的 JSON Schema 原样发出，不能"从 properties 重建"**：发给模型的工具定义由 `buildLLMTools`（`admAgent/internal/agent/agent_loop_llm.go`）产出。内置工具（反射生成）仍由 `{"type":"object","properties":…,"required":…}` 拼装，但 MCP 工具带的是服务端自己的完整 schema（`Tool.Info()` → `ToolInfo.Schema`，`internal/llm/agent/tool.go`），必须**逐字发出**：只取 `properties`/`required` 会丢掉所有同级关键字，后果分两类——① `$defs`（draft-07 是 `definitions`）被丢，属性里的 `$ref` 悬空，严格上游**在生成前**整包 400：`Invalid schema for function 'mcp_x_y': Pointer '/$defs/__schema2' does not exist`；② 根级 `$ref`/`allOf`/`anyOf`（pydantic `RootModel[Union[…]]`、zod `.and()`/`union` 都会生成）被丢，`properties` 取空，工具被当成"无参数工具"，调用必然缺参。用户侧表现为「发出后秒失败、重试报错一字不差」，或「工具永远缺参数」，而同一模型在没有该 MCP 的工作区完全正常（排查先确认是否只在特定工作区复现）。实现要点：`internal/agent/tools/mcp-tools.go` 的 `toolSchema()` 只在"根级引用/组合关键字解析后确属 object"时返回原文档（顺带补 `type:"object"`，**浅拷贝**、不改动服务端缓存的 schema），否则返回 nil 让 `buildLLMTools` 走老的重建路径；`isObjectSchema()` 判定 object 形状，`resolveTopLevelRef`/`lookupLocalRef` 负责根级 `$ref` 跟随（8 跳上限、带环检测）。回归用 `internal/agent/tools/mcp_tools_test.go` 与 `internal/agent/tools_schema_wire_test.go`——两者都断言发出的 schema 里每个本地 `$ref` 都能解到，且 `additionalProperties`/组合关键字不丢。

- **`view` 读图片（`admAgent/internal/agent/tools/view.go`）**：图片文件（PNG/JPEG/GIF/WebP/BMP，上限 `vision.MaxImageBytes`=20MB）不再被拒绝。按**主模型能力分流**（`coordinator.supportsImageViewing` → `NewViewTool` 的 `supportsImages` 参数）：`supports_images=true` 时返回 `image` 类型工具结果（`Data`+`MediaType`+一句文本，文本不能省——空 content 的 tool 消息会被严格上游拒绝）；纯文本主模型改走 vision bridge（`visionDescriber` 包装 `vision.Describe`，尊重 `agent_vision_model`）返回文字描述，避免图片 part 把会话打废。**图片必须额外搬运一次才能到模型**：OpenAI 兼容协议的工具结果只能放文本，所以 ① 当轮 `agent_loop_llm.go` 用 `toolResultWireMessages` 在 tool 消息后追加一条带 `image_url` 的 user 消息；② 后续轮次 `fantasyMessagesToLLM(history, supportsImages)` 把 tool 结果里 base64 的 media 重新搬成同样的 user 消息（同一段连续 tool 结果只产出一条，保持 tool 相邻、不破坏 tool_call 配对）。旧的无调用方的 `workaroundProviderMediaLimitations` 已删除。`agentic_fetch` 子 agent 用同一套 describer；摘要（`Summarize`）调用传 `supportsImages=false`，图片不进摘要请求。PDF 等其它二进制仍在非 UTF-8 分支被拒绝（只能前端转图后当附件发）。回归测试：`internal/agent/tool_media_wire_test.go`（转换层）+ `tool_image_loop_test.go`（mock provider 跑完整一轮，断言第二次请求体里出现 `image_url` 与 `data:image/png;base64,`）；真机形状验证脚本 `tmp/live_image_check`（`go run ./tmp/live_image_check [模型]`，用 admAgent.json 里的 provider 直连，2026-10-31 实测 `deepseek-v4.1-flash` / `glm-5.3-flash` 对"tool 消息 + 带图 user 消息"均正常返回图像颜色）。

- **推理强度档位按 provider 模板自动降级（`internal/llm/client.go`）**：本地 GGUF 的内嵌 Jinja 模板可能只接受自己的词表——2026-11 日志里 `Qwen3.8-27B-Uncensored` 模板只认 `xhigh (default) / medium / low`，ADM 工具栏发 `high` 时 llama-server 在渲染阶段 `raise_exception`，以 HTTP 500 返回 `Unexpected reasoning effort high. Supported types are …`，整轮直接中断。现在 `Client.Stream` 识别该错误（500 与 400 都算），解析 `Supported types are …` 列表，按 `none < minimal < low < medium < high < xhigh < max` 取最近档（平局取更高档，因此 `high` → `xhigh`），重试一次并把 `baseURL+model+requested → mapped` 缓存 30 分钟——后续每步请求直接发支持值，不再每步白跑一次失败请求；缓存过期或模型切换导致模板变化时，若映射值仍被拒，会以**用户原始档位**重新映射并删除旧缓存（自愈）。这类错误在 `isRetryable` 中显式判为不可重试，否则 5xx 会先按退避重试 3 次才轮到降级。**「关闭推理」（`none`/`off`）不降级**：把“关闭思考”悄悄改成活跃档位会违背用户选择，统一返回既有的 `thinking_mode_unsupported` 契约（400 + title），决策轮照旧自动去掉参数重试，普通轮由前端提示切回思考档。回归：`internal/llm/reasoning_effort_fallback_test.go`（降级+缓存、不重试、模型切换自愈、解析/映射表）。

## 工作区生命周期与切换性能（服务端）

桌面端“切换工作目录”的卡顿主要来自建工作区/初始化 Agent 的重复劳动，以及每次切换都写配置文件。服务端侧的约定（改动这些路径前先读）：

- **服务工作区不再自动建 coordinator**（`internal/backend/backend.go` 的 `CreateWorkspace` 传 `app.WithDeferredAgentInit()`）：`app.New` 只装配 sessions/messages/permissions/LSP/skills 等服务，不调 `InitCoderAgent`。agent 由前端显式 `POST /v1/workspaces/{id}/agent/init` 构建一次。**为什么**：桌面端首访本来就紧跟着调 `/agent/init`，两边都建就是每个工作区两遍完整 coordinator（各开一个 rail3.db 连接、各建一个 task 子 agent；日志里每次建工作区都能看到两条 `buildTools: agentTool done`）。本地 TUI（`internal/cmd/root.go` 的 local 模式）仍走 `app.New` 的默认自动初始化。
- **`/agent/init` 幂等，替换前先 `Close`**（`internal/backend/agent.go` 的 `InitAgent`、`internal/app/app.go` 的 `InitCoderAgent`）：已有 coordinator 时直接返回（`Workspace.agentInitMu` 串行化并发 init）；确实需要重建时先 `old.Close()` 再换指针。旧实现直接覆盖字段，每重建一次泄漏一个 rail3.db 句柄（Windows 上还持文件锁）。`/agent/update` 仍是“重载模型 + 工具目录”的入口，不依赖 init 重建。
- **配置版本号 `ConfigStore.Revision()`**：`setConfig` 每次发布新的 `Config` 快照就自增。派生缓存用它做失效判断，**不要**再按“每轮都重建”兜底：
  - `coordinator.agentTool` 缓存 task 子 agent（`taskTool` + `taskToolRev`），模型/技能/配置不变时直接复用。`UpdateModels` 每轮开始都会重建工具目录，原先每次都要重新构造 task 子 agent（冷缓存实测 ~1s、热 ~50ms）。
  - 新增任何“只有配置变化才需要重算”的缓存都走同一个 revision，别自己再发明一个计数器。
- **rail3 孤儿清理每数据目录只跑一次**（`internal/agent/agent.go` 的 `buildContextManager` / `reconcileRail3Once`）：`Sessions.List` + `Reconcile` 从“每个 SessionAgent 每次构建”降为按 dataDir 进程内只跑一次（`reconcileStates` 守卫），且子 agent（`IsSubAgent`）完全跳过——父 coordinator 已在同一工作区做完。守卫只在**成功**后置位：`Sessions.List` / `Reconcile` 瞬时失败会在下一次 agent 构建时重试，不会像裸 `sync.Once` 那样把 GC 关到进程重启。清理是维护任务，没必要在每轮开始前重复扫表。
- **系统提示词复用工作区技能快照**（`internal/agent/prompt` 的 `WithSkillSnapshot`）：coordinator 构建时把 `activeSkills` 传给 prompt，`prompt.Build` 不再自己 `skills.Discover` 走一遍技能目录。不传快照的调用方（如 `InitializePrompt`）保持原行为。
- **git 快照合并成两次子进程 + 10s TTL 缓存**（`internal/agent/prompt/prompt.go` 的 `getGitSnapshot`）：`git status --porcelain=v2 --branch` 一次同时给出“是不是仓库 / 当前分支 / 改动列表”，再跟一次 `git log --oneline -n 3`；旧实现是 `rev-parse` + `branch` + `status` + `log` 四次 spawn（Windows 每次 ~20ms）。同一工作目录的 coder 与 task 两个 prompt 共享缓存。
- **MCP 初始化是进程级单例且带引用计数**（`internal/agent/tools/mcp/init.go`）：`Initialize` 按 `cfg.MCP` 的 JSON 签名去重（签名不变直接跳过，日志里不再每次建工作区都刷 “Initializing MCP clients”）；`Close` 按 `initRefs` 递减，只有最后一个工作区关闭时才真正关会话——此前任一工作区 teardown 会把别的工作区仍在用的 MCP 会话关掉。**事件 broker 是进程级单例，创建后永不替换、也不在 `Close` 里 shutdown**：`SubscribeEvents` 的订阅方按工作区各持一条 channel，运行时替换 broker 既是对包级变量的数据竞争，也会让旧订阅悄悄失聪；订阅方在自己的 ctx 取消时自行退出（`pubsub.Broker.Subscribe`），无需显式关闭。
- **切换相关耗时进日志**：`CreateWorkspace` 打 `CreateWorkspace: app ready` / `CreateWorkspace done`（带 elapsed），`InitAgent` 打 `InitAgent done`（elapsed + error）。排查“切目录慢”先看这三条与 `buildTools: agentTool done`、`UpdateModels: done`。
- **配置写入的两个省流点**：`/config/reload`（见 `doc/server-api.md`）取代“回写同一 api_key 触发 autoReload”的切工作区副作用；`SetCompactMode` 发现目标值与当前一致时直接返回，不写盘、不发布新快照（前端每次激活工作区都会再确认一次 compact=on）。

## 工具与权限边界

- **工具参数的数值边界：范围型 clamp，语义型硬错误**（`internal/agent/tools/grep.go`、`internal/llm/agent/schema.go`）：只影响展示/结果体量的参数（`grep.context` 0-10、`fetch.timeout` 0-120、`web_search.max_results` 0-20）越界时由 `normalized()` 钳制，并在工具结果首行写明 `[note: context 14 clamped to 10 (allowed 0-10)]`，不返回错误——实测 `deepseek-v4.1-flash` 会稳定给出 `context: 14`/`15` 这类值，硬报错要浪费一整轮，且同一工具连续失败 3 次会 nudge、5 次直接结束回合（`loop_detection.go`）。会改变搜索语义的参数（`sort`/`modified_after`/`file_types`）保持硬错误；`preview` 只影响呈现，因此按别名归一（`content`/`text`/`matches`→`lines`、`files`/`file`/`file_paths`/`files_with_matches`→`paths`、`raw`→`full`，这些词汇来自其它 grep 工具的 `output_mode`），其余未知值回落 `lines` 并在首行写 `[note: preview "content" mapped to "lines" (allowed: …)]`——不能因为一个展示开关让整次搜索失败并累计熔断。**枚举型取值写进 JSON Schema**：struct tag `enum:"mtime,path"` / `enum:"lines,paths,full"`（`grep.sort` / `grep.preview`）与 `enum:"incoming,outgoing"`（`lsp_call_hierarchy.direction`）由 `schema.Generate` 解析、`ToMap` 发出，模型不必只靠描述文字猜合法值。数值边界同样通过 struct tag（`minimum:"0" maximum:"10"`，`schema.applyNumericBounds`）进 schema。回归：`TestGrepToolClampsContext`、`TestGrepToolFallsBackOnUnknownPreview`、`TestGrepToolContextSchemaBounds`、`TestGrepToolAdvertisesEnums`、`TestGenerateNumericBounds`（含 NaN/±Inf 被忽略）、`TestToParametersEmitsEnum`。**参数校验失败**（`dur_ms=0`）与 **`stale_read` / `must_read` 拒绝**在 `Loop tool result` 里带 `error_text`（截 200 rune）：前者可直接看出是哪个参数越界，后两者是工具自己生成的（路径 + 两个 mtime 或一段当前内容），排查被拒的编辑不必再翻会话库；其余执行类错误不记录错误原文（fetch 的 URL / 命令输出可能带凭据），input 也始终不记录（bash 命令可能含密钥）。数值 tag 的 NaN/±Inf 按非法值忽略，避免 JSON 无法编码导致 `buildLLMTools` 把该工具 schema 静默退化成 `{}`。
- **MCP 资源工具的注册与取错：按"有没有可用 server"判定，错误要能自我纠正**（`internal/agent/coordinator.go:781`、`internal/agent/tools/list_mcp_resources.go`、`internal/agent/tools/read_mcp_resource.go`、`internal/agent/tools/mcp/init.go` 的 `unknownServerErr`）：① 注册条件从 `len(cfg.MCP) > 0` 改成 `len(cfg.EnabledMCPNames()) > 0`（`internal/config/config.go`，过滤 `disabled`、排序）——配置里只有被禁用的 server 时不再把 `list_mcp_resources`/`read_mcp_resource` 挂给模型，否则模型没有任何合法 server 名可填，弱模型会填占位符（实测 `deepseek-v4.1-flash` 传 `{"mcp_name":"none","uri":"none"}`，日志 `Loop tool result ... error_text="mcp 'none' not available"`）。② `list_mcp_resources` 的 `mcp_name` 改为可选：省略时遍历全部可用 server，输出按 `- [server] title (uri): desc` 分服务器罗列，单个 server 报错只占一行（`- [name] error: …`），不掩盖其它 server 的资源；显式传名时输出格式与旧版一致。这条是唯一的 URI 发现通路，此前的 schema 强制要求 `mcp_name` 等于"要名字才发现名字"，鸡生蛋。③ 两个工具在进入 MCP 层之前拦占位符（`placeholderMCPNames`：`none`/`null`/`nil`/`n/a`/`na`/`unknown`，大小写与空白不敏感），返回`mcp_name must be a real MCP server name; omit mcp_name to list resources from every enabled server`；真正的未知名由 `unknownServerErr` 回 `mcp '<name>' not found; enabled MCP servers: <名单>. Call list_mcp_resources without mcp_name …`，禁用项单独说 `mcp '<name>' is disabled`。这些是普通工具错误、不是 `Tool not found`，`loop_detection.go` 的不可用工具 nudge 不会介入，所以错误文本本身必须带纠正方向。回归：`internal/config/mcp_enabled_names_test.go`、`internal/agent/tools/mcp_resource_tools_test.go`、`internal/agent/tools/mcp/unknown_server_test.go`。
- **撤销数据清理只认单段会话 ID**（`internal/undo/snapshot.go` 的 `PurgeSession`）：`sessionID` 来自 `DELETE /v1/workspaces/{id}/sessions/{sid}` 的路径段，Go 1.22 的 mux 会把 `%2F`/`%2e%2e` 解码出来。命名空间是 `path.Join(refs/admAgent/undo, sessionID)`，`sessionID="../../heads"` 会被清理成 `refs/heads`，随后 `for-each-ref` + `update-ref -d` 把本地分支全删掉。现在入口用 `isSingleRefComponent` 拦住非单段值（空串、`.`、`..`、含 `/` 或 `\`）并打 `Undo purge skipped: invalid session id`。**新增任何"用 sessionID 拼 git ref / 拼路径"的入口都要过同一道校验**；附件目录那边用的是 `safeSessionComponent`，别各自发明。
- **bash 只读自动放行列表的边界**（`internal/agent/tools/safe.go`）：`safeCommands` 只放"无文件/进程/仓库副作用"的程序，`kill`/`killall` 曾误列其中，导致 `kill -9 <pid>` 不弹权限提示就能终止用户的编辑器/测试进程，现已移除。标为只读的 git 子命令（`diff`/`log`/`show`/`grep`/`rev-parse` …）也不再无条件放行：`--output`、`-O<cmd>`、`--open-files-in-pager`、`--ext-diff`、`--exec-path` 会把只读子命令变成写文件或执行命令（`git diff --output=/path`），一律降级为需要授权。回归测试 `TestIsSafeGitCommandRejectsWriterAndExecFlags`、`TestSafeCommandsExcludeProcessTermination`。
- **工作区内 edit/multiedit 免提示的包含性判断**（`internal/permission/permission.go`）：自动批准依赖 `filepath.Rel(workingDir, dir)`，父目录恰好返回 `".."`——它不以 `".."+分隔符` 开头，早期写法会把它当成"工作区内"直接放行，等于把沙箱边界放宽一层。现在显式排除 `rel == ".."`。回归测试 `TestPermissionService_EditAutoApproveStaysInsideWorkingDir`。
- **越界读取判定按真实路径**（`internal/agent/tools/view.go` 的 `resolveForContainment`）：`filepath.Abs` 不解析符号链接，工作区内一个指向 `~/.ssh/id_rsa` 的链接在词法上是子路径，读它不会触发越界权限请求。现在比较前对目标（不存在时回退父目录）和工作区都做 `EvalSymlinks`。新增任何"路径是否在工作区内"的判断都按这个标准，别回到纯词法比较。
- **edit/multiedit 的漂移匹配必须拒绝多义**（`internal/agent/tools/edit.go` 的 `uniqueMatch`）：空白容错/fuzzy/ngram 分支返回的是"匹配到的原文块"，不返回位置，调用方再用 `strings.Index` 重新定位——块在文件更早处也逐字出现时就会改错区域且报成功。现在这三条分支命中后先确认该块在文内唯一，否则返回 `matchAmbiguous` 让模型补上下文。
- **old_string 的"尾随空行 + 行中片段"必须能命中**（`edit.go` 的 `sanitizeEditStrings` / `oldStringVariants` / `locateNormalizedSubstring` / `finalizeTolerant` / `extendTrailingNewlines`）：模型常把 `old_string` 写成"块 + 一个空行"（`…任务\n\n`），而文件里是 `…任务\n25. …`；如果这块还从一条 482 字符长行的行中间开始，四条旧策略全部落空——空白容错只按整行块比较（长行前缀不匹配），fuzzy 的首行锚点拿整行跟片段算编辑距离（远超阈值），ngram 定位到了但相邻窗口因含同一条长行而得分并列、被唯一性检查判负并直接报 `not found`。现在的顺序是：`old_string` 生成变体（逐字 → 去掉尾换行 → 各自再 strip view 行号/标签，去重后按序尝试），每个变体先做精确计数，再依次走归一化子串 → 空白容错 → fuzzy → ngram；**归一化子串**（`locateNormalizedSubstring`）把两边的 ASCII 空白折叠成一个空格并用偏移映射还原原文区间，因此行中片段、内部双空格、跨行空白差异都能命中，且不会像整行滑窗那样把整行替换掉；命中后 `extendTrailingNewlines` 按文件实际拥有的换行把模型多写的尾换行接回去（多写的空行丢弃、文件自身的换行保留，新内容以换行结尾时不会多出空行）。ngram 的并列判定改为 `matchAmbiguous`（不再是 `not found`），`buildOldStringNotFoundError` 用 trigram 最相似行回吐就近窗口（带行号）而不是文件头。回归：`edit_match_test.go` 的 `TestMatchOldStringMidLineFragmentWithTrailingNewline` / `TestMatchOldStringNormalizedSubstringInternalWhitespace` / `TestLocateNgramFallbackReportsAmbiguous` / `TestBuildOldStringNotFoundErrorShowsNearestWindow`。
- **edit 的 no-op 拒绝必须给出下一步**（`internal/agent/tools/edit.go` 的 `replaceContent`）：参数清洗后 `old_string == new_string` 的调用在读文件/匹配之前直接拒绝（文案 `old_string and new_string are identical …`），否则它会走完整条容错匹配链才落到"整文件内容不变"的兜底分支；该兜底分支只留给**幂等重试**（两个参数不同，但容错匹配把 `old_string` 落到已等于 `new_string` 的原文上，典型是上一次编辑已生效又重试），文案为 `the file already contains new_string … already applied`，避免模型把"文件不会变"误读成匹配失败而在原地反复重试。回归：`internal/agent/tools/edit_noop_test.go`（相同参数 / 已生效重试两条）。
- **multiedit 兼容 edit 形状的参数，缺参错误必须自解释**（`internal/agent/tools/multiedit.go` 的 `MultiEditParams.UnmarshalJSON` / `missingEditsMessage`）：2026-11-26 的日志（`Loop tool result tool=multiedit error=true tool_result_tokens=10`，同一步 `tool_calls=2`）与落库原始入参显示，`deepseek-v4.1-flash` 在"一步发多条单条替换"时会把每条写成 `edit` 的两字段形状 `{"file_path","old_string","new_string"}`；Go 解码默认丢弃未知字段，`edits` 为空，只回 `at least one edit operation is required`，模型只看到 "glitch"，同会话原样重试 3 次（11:31、11:50、12:45）。现在解码层接受两种偏差：① 顶层 `old_string` + `new_string`（可带 `replace_all`）合成单条 `edits`，成功时结果尾部加一行 `Note: the flat old_string/new_string was interpreted as edits[0]…`；② `edits` 传成单个对象时按一元数组处理。**只有 `old_string` 不当作删除**——空 `new_string` 的删除语义会让一次猜测直接抹掉内容，宁可报错；此时错误列出实际收到的顶层字段（排序）并给出正确形状与 `edit` 工具替代，不再让模型盲猜。工具描述不写这些示例：`prefixBudgetTokens` 只剩约 200 token 余量（见 `doc/admAgent-prefix-budget-plan.md`），形状兼容放在解码层不花前缀成本。回归：`internal/agent/tools/multiedit_test.go` 的 `TestMultiEditParamsAcceptsFlatShorthand` / `TestMultiEditParamsAcceptsFlatCreation` / `TestMultiEditParamsAcceptsSingleEditObject` / `TestMultiEditParamsKeepsCanonicalShape` / `TestMultiEditParamsFlatOldStringAloneIsNotAnEdit` / `TestMultiEditToolAppliesFlatShorthand` / `TestMultiEditToolMissingEditsNamesReceivedFields`。
- **写文件后通知 LSP 用解析后的绝对路径**：`write` 曾把未解析的 `params.FilePath` 传给 `notifyLSPs`，而 `lsp.Client.HandlesFile` 要求工作区绝对路径前缀，相对路径被判 false → 不发 `didChange`，紧随其后的 `getDiagnostics` 返回写之前的诊断。`edit` 早就是把 `params.FilePath` 回写成 `SmartJoin` 结果，`write` 现已改传局部变量 `filePath`。
- **读后写守卫：读后校验，而不是先拒绝**（`internal/agent/tools/staleread.go`，接入 `edit.go` 的 `replaceContent`/`deleteContent`、`multiedit.go`、`write.go`）：守卫原先在 `os.ReadFile` 之前比较 `fileInfo.ModTime()` 与本会话 `read_files.read_at`（秒级），mtime 前进就整单拒绝。`gofmt -w` / `sed -i` / IDE 保存这类**绕过编辑工具**的写入不更新读记录，于是模型自己刚格式化过的文件也会被拒，模型刚 grep 到锚点、没 view 就直接改同样被拒：恢复要 view + 重试两步，且每次拒绝都计入 `consecutiveToolFailures`（3 次 nudge、5 次结束回合）。现在判断挪到读入当前内容之后，并把读记录与 mtime 都当**代理**：编辑真正的先决条件是 `old_string` 在当前内容里精确唯一匹配。① 本会话**从未读过**（`lastRead.IsZero()`）或 mtime 前进，但锚点仍精确唯一匹配（多远编辑按顺序模拟；不容错/模糊匹配）→ 照常写入，结果尾部加 `Note:`（过期是 “changed on disk … still matched exactly”，未读是 “this session had not read … read it before relying on anything else”）；② 锚点不匹配且**从未读过** → `must_read: ` 前缀 + `<actual_file_content>` 当前内容；③ 锚点不匹配且读过 → `stale_read: ` 前缀 + 当前内容。②③ 在整文件时同时 `RecordRead` 刷新读记录（重试一步即可），超过 `fileContentSnippet` 上限则提示先 view。回传的 `<actual_file_content>` **只在目标位于工作区内时附带**（边界与 `view` 一致：`resolveForContainment` 解析符号链接后再 `filepath.Rel`，`rel == ".."` 不算；工作区内指向外部的符号链接按外部处理）；工作区外只返回文案、让模型走 `view` 触发越界权限请求——`edit`/`multiedit`/`write` 的 `permissions.Request` 发生在守卫之后，守卫回传内容等于无提示越界读取。回归：`TestGuardWithholdsContentOutsideWorkingDir`。`stale_read` / `must_read` 是稳定分类键：`stale_read` 不计入连续失败熔断（外部写入不是工具缺陷）；`must_read` 在 `edit`/`multiedit` 照常计数（锚点对不上是模型自身的输出错误），`write` 的 `must_read` 不计入（全量覆盖无锚点，文件常由 bash 重定向/其他会话先行创建；拒绝已回传当前内容并在整文件时刷新读记录，重试一步即成功；若按工具缺陷计数，一次 scaffold 多个 go:embed 占位文件就会撞 3 次 nudge / 5 次结束回合）。`write` 未读与过期都硬拒，文案单独说明「全量覆盖、没有 old_string 可校验」，不再复用 edit 的锚点措辞；`write.md` 提示新建文件（含占位文件）直接用 `write`，不要 bash 重定向。桌面端按 `is_error` 显示「失败」。`bash` 成功后额外 stat 最近 20 个已读文件，被命令改过的在结果尾部列出（`<read_files_changed>`），把问题暴露在发生的那一步。同目录并发写仍由 `filelock.go` 串行化。回归：`internal/agent/tools/staleread_test.go`。

## 网络代理链路

- **网络代理链路**（设置→网络代理，仅影响 admAgent，桌面端下载不走代理）：
  1. 前端 `settings.js` `saveProxy()` 校验（启用时 url 必填、须以 `http(s)://` 或 `socks5://` 开头）→ `save_settings` 写入 config.json 的 `agent_proxy`。
  2. Rust `settings.rs:37` 调用 `agent.rs` `sync_agent_proxy`：`write_agent_proxy`（`agent.rs:640`）把 `{enabled,url}` 写入 admAgent.json 顶层 `agent_proxy`（原子写，值未变返回 false 跳过）→ 有变更时对当前 active workspace `POST /v1/workspaces/{ws}/config/set` 触发服务端**磁盘全量重载**（10s 超时，失败仅记日志退回直连）。
  3. admAgent `ConfigStore.setConfig` 把代理同步到进程级 `httpproxy`（`internal/config/store.go:100-105`）；`httpproxy.ProxyFunc()` 作为 `Transport.Proxy` 回调**每次请求实时读取**状态，热重载即刻生效、无需重建 client/重启 server；本地/私网地址（127.0.0.1、LAN GPU 盒）自动绕过（`internal/httpproxy/proxy.go:50-81`）。
  4. **生效范围**：LLM 客户端（`llm/client.go:107`）+ Agent 网络工具 fetch/web_fetch/download/web_search/sourcegraph/agentic_fetch（全部经 `SharedHTTPTransport`，`tools/fetch_helpers.go:38-48`）；**MCP HTTP/SSE 传输不走**（`mcp/init.go:538-581` 用 `http.DefaultTransport`，只认 `HTTP_PROXY` 环境变量）。注意：面板文案"仅影响 LLM 请求"比实际范围窄，工具类请求同样走代理。


## LSP 托管安装（服务端）

- **状态与修复 API 化**：LSP 状态、`reason`/`fix`/`guide`、安装、修复、回滚、卸载、job 进度统一由 `admAgent` 提供；桌面端只消费 API/SSE，不执行 `npm -g`/`pip`，不 patch `admAgent.json`。
- **目录与锁**：默认 `<GlobalCacheDir()>/lsp`，可用 `lsp_install_dir` 覆盖；安装按 `servers/<name>/<version>/` 隔离，`state.json` 由 `.locks/state.lock` 跨进程串行化并原子写；安装命令本身由 `.locks/<name>.lock` 串行化。
- **manifest**：`internal/lsp/managed/catalog.json` 随二进制嵌入，版本 pin 死；manifest 提供 runtime、package、入口、filetypes、root markers、license/source/guide，与 powernap 同名时 manifest **整体替换** powernap 条目（`refreshManaged` 走 `AddServer`，不是字段合并）。因此 manifest 的 `rootMarkers` 不得比 powernap 默认更窄：gopls 必须保留 `.git`（powernap 默认 `go.work`/`go.mod`/`.git`），否则工作区根目录没有 `go.mod`/`go.work`（Go 模块在子目录，如本仓库 `admAgent/`）时 gopls 不会自动启动，`lsp_*` 工具报 `no LSP client handles file`；单测 `TestManagedGoplsRootMarkersKeepGit` 守护。
- **运行时选择**：`options.lsp_runtime_preference=system|managed`（默认 system）；P0 使用系统 Node/Python/Go，托管 runtime 下载在 P2。`options.lsp_managed_runtime=ask|auto|off` 控制下载策略；桌面端自动修复触发已移除，只保留手动修复。
- **API**：`GET /v1/lsp/catalog`、`POST /v1/lsp/doctor`、`POST /v1/lsp/install|fix|uninstall`、`GET /v1/lsp/jobs[...]`、`POST /v1/lsp/jobs/{id}/cancel`，以及按名称 `POST /v1/workspaces/{id}/lsps/{lsp}/start|restart`；显式 `start|restart` 绕过 `auto_lsp`、root markers 与不可用冷却；`GET /lsps` 的 `LSPClientInfo` 增加 reason/fix/guide/runtime/server_version/managed。
- **fix 判定**：托管目录有 active 版本、或系统 PATH 已能解析到 manifest 入口（`exec.LookPath` 命中）时不下发 `fix`；`GET /v1/lsp/catalog` 同样跳过已在 PATH 上的服务器。否则系统安装（如 `~/go/bin/gopls`）会被误判为 `missing_package`，在已连接的客户端旁边显示「安装」。
- **发现**：`lsp.NewManager` 同时加载 powernap、用户配置与 `state.json` 中的托管安装；托管安装不写用户配置，`TrackConfigured`/面板包含托管项；安装后可 `StartByName` 强制刷新。
- **安全**：安装/修复端点只接受 manifest 内 name/version（修复另允许当前 active / previous 版本）；命令用 `exec.Command` 参数数组，不拼 shell；安装目录 0700；下载/日志不写代理凭据。默认仅本机访问，非 loopback 需 token（P0 未实现 token，沿用现有 server 访问边界）。
- **CLI**：`admAgent lsp list|doctor|install|repair|uninstall|jobs|cancel`，与 API 共用 `internal/lsp/managed`。
- **已知未完成**：离线 pack、API token、自动修复触发；SSE、单主过滤、桌面切换与 Node 托管 runtime 已接入。
