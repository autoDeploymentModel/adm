# admAgent 服务端约定与调优

> 范围：服务端（Go）行为与前后端契约 —— Agent loop 抖动恢复、上下文压缩与事实块、系统提示词预算与提示词缓存、归档编号、决策输出模式、代理链路、配置词表。改动前先读本文对应小节。

## Agent loop / 上下文压缩 / 决策模式

- **Agent loop 抖动恢复体系**（`admAgent/internal/agent/agent_loop_llm.go`）：空 stop 重试（上限 3）、叙述性 stop 重试、推理超限（软阈值统一 `reasoningOverrunMaxTokens` = 120000 **估算 token**，**不再按 reasoning_effort 分档**；估算规则 ASCII ≈4 字节/token、非 ASCII rune 计 1 token，见 `outputDegradationDetector.tokens`；超限或 max_tokens 被推理吃光时丢弃+nudge，上限 2 次）、未完成 todos nudge（**进度感知**：连续 3 次无进展才放弃，有进展（todo 完成或 edit/write/bash 等实质副作用工具成功）即清零计数，硬熔断总上限 10 次；**文案必须点名 `todos` 工具**——2026-10-28 实测：只列 "read, edit, write, bash, grep" 的泛化文案被弱模型读成"继续用 bash 复检"，93 步里只有 1 次 `todos` 写入，10 次 nudge 全部照旧，面板停在 0/4；`todoNudgeEscalateAfter`=3，从第 3 次起文案升级为"要么用 `todos` 回写完成态、要么继续干活，禁止再输出空泛正文"）、**运行中 todo 状态提醒**（`todoStatusLine` + 两个文案构造器：轮首用 `todoStateReminder`、运行中用 `todoProgressReminder`。轮开始时清单仍有未完成项 → 先发一次；此后每 `todoProgressReminderEvery`(3) 次成功的实质副作用工具调用（`todos` 之外的 edit/multiedit/write/bash/改符号/rename/download）都没换到一次 `todos` 回写 → 再发一次。文案带 `N/M completed (i in progress, p pending)` + 当前项/下一个待办 + "禁止攒到最后批量回写"，点名 `todos` 工具；上限 `maxTodoProgressReminders`(8) 次/轮，`todos` 回写成功即清零计数；列表为空或全完成时静默。**轮首那条必须写成条件式**（"if the current request continues that task … otherwise ignore this reminder"）：旧清单可能属于用户已经换掉的话题，只有模型能判断本次提问是否延续它；改用提问关键词闸门不可行——`isLikelyCodingTask` 只认英文动作词，"继续" 与一句无关中文提问对它完全同形。**只走尾部 wire-only nudge**，不碰系统前缀。存在的理由：模型上下文里唯一的清单信号是它自己早先那次 `todos` 调用，长回合会漂成"最后一次性批量回写"——2026-11-08/09 日志（≥20 步的 40 个 run）里 17 个用到 todos，其中 12 个**恰好 2 次调用**（开头建表 + 倒数 3 步内标完成），`2026-11-09 19:40` 那个 run 只有 step 18 一次、其后 83 步全无，面板整轮停在 0/9）、假完成检测。正常结束（无 error / 未取消）时 `run_complete.incomplete_todos` 携带剩余未完成数（`session.CountIncompleteTodos`），桌面端据此提示"任务清单还有 N 项未完成"，避免终稿宣称完成与面板 0/N 互相矛盾。每次「丢弃半成品并重试」前先推一条 `agent_event type=thinking`（`progress` 为稳定 token：`discard_reasoning_overrun` / `discard_stream_interrupted`，见 `notifyDiscard`；桌面端 `DISCARD_NOTICE_TEXT` 额外保留已不再发出的 `discard_reasoning_timeout` 一个版本周期，防止旧 sidecar 的提示退化成英文 token 原文），桌面端 `sse.js` 按 token 提示“思考被丢弃并重新生成”（旧版服务端无该事件时按被删消息内容兜底）——否则用户只看到思考气泡凭空消失（表现为“思考很久 → 突然清屏 → 又继续思考”）；TUI 忽略 thinking 通知（`internal/ui/model/ui.go` 的 default 分支）不受影响。重试耗尽后本轮**无 error 静默结束**（run_complete 不带错误），UI 侧表现为“突然停了”。
- **空正文提示 + empty_output**：step 流式输出只有 reasoning、无正文/工具调用时，每 60s 推一次 `agent_event type=thinking`（progress 带已思考秒数，前端 `showInfo` 提示“模型仍在思考…”）。这是**纯提示、不打断**：思考时长不设上限（原 `emptyTextNudgeAfter` 300s 看门狗已删除），单步只有 `reasoningOverrunMaxTokens` 这个 token 预算在约束。本轮正常结束但无任何输出（正文与工具调用皆无，或 assistant 消息被丢弃）时 `run_complete` 携带 `empty_output: true`，前端提示“模型未产生有效输出”且不自动续跑。
- **重复工具调用检测对“后台任务等待”豁免**（`admAgent/internal/agent/loop_detection.go`）：`hasRepeatedToolCalls` 按 `tool+input+output` 签名计数，10 步窗口内同一签名出现 >5 次（`loopDetectionMaxRepeats`）即判定卡死并结束本轮。`job_output` 轮询仍在运行的后台 shell 时结果恒为 `Status: running` + 固定提示文案（`agent/tools/job_output.go`），签名天然相同——实测连续 6 次 `wait=true`（每次 30s）就把一轮健康任务在 ~3 分钟处 `ending turn`，本轮无 error 无正文，用户看到的是“对话自己结束了”（2026-11-01 日志 3 次全部此形态）。现在**只含 `job_output` 且结果为 `Status: running` 前缀的步骤不计入签名**（`isPendingJobPoll`，混合步骤仍计数，`Status: completed` 的重复读取仍会被抓）；豁免有界：单轮等待轮询超过 `jobPollWaitMaxSteps`(40，≈20 分钟) 后恢复计数，避免 dev server / watcher 这类永不结束的任务把回合拖到步数触顶。单测见 `internal/agent/loop_detection_test.go`（等待豁免 / 上限 / 完成后重复 / 混合步骤四条）。
- **回合 panic 隔离 + `admAgent-panic.log`**：`SendMessage` 用 `go b.runAgent(...)`（`internal/backend/agent.go`）把回合派发到脱离 HTTP 请求的 goroutine，`net/http` 的 `recoverHandler` 覆盖不到——一次未捕获 panic 会带走整个 server 进程，桌面端表现为“服务异常退出，正在自动重启”且当轮对话凭空消失。现在 `runAgent` 自带 `defer recover()`：`slog.Error` 记一条带 `stack` 的 ERROR，`log.WritePanic("agent.run", …)` 追加到 `%LOCALAPPDATA%\admAgent\cache\admAgent-panic.log`（同目录、只追加、超 8MB 轮转 `.prev`），并通过 `publishRunFailure` 给 RunID 等待方发 errored `run_complete`（已发布过终态则不重复）。`recover()` 抓不到的 fatal（并发 map 写、栈溢出、OOM）由 `log.Setup` 里的 `debug.SetCrashOutput` 写入同一文件；`log.RecoverPanic` 也从原来的“当前目录 timestamped 文件”改为追加到这里。注意 `admAgent.log` 仍在每次启动时截断，崩溃后**不要**只翻它。
- **压缩摘要的确定性事实块**（服务端 `internal/context/facts.go`）：每次压缩在摘要前缀（`---` 围栏内、Rail 0 anchor 之后）追加一段**代码抽取、模型不参与**的 `[Session Facts]`：`Modified`（`edit/multiedit/lsp_replace_symbol` 的 `file_path`）、`Created`（`write`）、`Commits`（bash 的 `git commit -m` 主题 + 紧随 tool_result 里的短 hash）、`Archived`（归档编号区间 + `range/expand` 用法提示）；`Read` 段默认关（`options.fact_block_read` 打开后由 `filetracker.ListReadFiles` 注入，**不要**改用 filetracker 的写记录——它是内存态 + 10 分钟 TTL）。整块 600 字符上限、每类 10 条 + `(+N more)`、路径裁到最长公共目录前缀；总开关 `options.fact_block`（默认 true，nil=开）。生命周期与 anchor 块完全对齐：`CompactWithBudget` 从上一版摘要 `MergeFromText` 解析回来 → `StripFactBlock` 剥掉后才归档 → 下次重新渲染，故不会重复累积；**`carryForwardSummaries` 必须同时剥 anchor 与 fact 两个块**（漏一处每轮叠一层）。
- **归档编号 `#N` 的三条不变量**（摘要/事实块里的 `(#1253)` 与 `recall` 同构）：① 编号 = 会话内消息序号（`messages.List` 的 `created_at, rowid` 顺序，`getSessionMessagesWithIndex` 产出 map），归档条目用现成的 `Entry.Turn` 承载，**不必加新列**；② 已归档条目永不被删除（撤销/丢弃只删活动上下文尾部），归档时编号被占用则顺延 `max+1`（`claimTurn`），保证 `#N → 条目` 唯一可解；③ 升级后**首次压缩该会话时必须 `BackfillTurns` 回填**旧条目的局部编号（映射不到的消息置 `-1` = 不可寻址），漏做会让 `expand:[N]` 静默返回错误条目。`recall` 工具新增 `range:[a,b]`（20 条/页）、`expand:[N]`（≤5 条，单条 `recallRefEntryTokens`=1200 token、总预算 2000 token；工具描述写的是"capped at ~1200 tokens each"，不要再写成 FULL untruncated）与"未用参数点名 / 越界明说 / 下一步提示"；取回走 `Store.LoadByTurns`（无 store 时用内存 `memEntries`）。被动 `RecallStrict` 注入路径未改。方案与实施记录见 `doc/admAgent-fact-block-and-recall-refs-plan.md`。
- **上下文窗口下限与压缩经济性（服务端 `internal/agent/agent.go`）**：设计目标是 **≥128k 窗口**（`recommendedContextWindow`）。判定式：`可用工作窗口 = guard(cw) − 固定开销 − 2×摘要上限`，要求 ≥ `minUsableWorkWindow`(25k)；固定开销在运行时实测（系统提示/前缀/项目记忆 + 工具 schema），不写死常量：2026-11 精简系统提示后，本仓库 27 工具实测 ≈ 14.1k（系统提示 7.2k + 工具 schema 7.0k，每工具 ≈ 259 token），精简前是 ≈ 19.0k；再把 bash 描述里的 git/PR 剧本（5.2k 字符）搬进 `git-commit` skill、工具描述去重、`<project_structure>` 收到 depth 2 之后，同一套 27 工具实测 **≈ 8.9k（系统提示 3.2k + 工具 schema 5.7k，最大单工具 bash 0.9k）**。64k 窗口下可用窗口约 ~13k（**每 4–5 步就要压缩一次**，每次 15–70s，本地模型实测占墙钟 ~25%），32k 下固定开销直接超过 guard（压缩永远落不了地）。低于该线时 `Summarize` 会打 `context window leaves a small work window` 警告（带 work_window_tokens/fixed_overhead/advice），提示改窗口或精简工具目录/系统提示。**固定前缀有了硬预算**：`prefixBudgetTokens`(9200)、`maxToolPrefixTokens`(1500/tool)、`maxToolCatalogueSize`(32) 三个常量 + `TestPrefixBudget`（`internal/agent/prefix_budget_test.go`，用生产 `buildTools` 与 `prompt.Build` 实测，不烧模型调用）把闸门放进单测；`coordinator.run` 在 `readyWg.Wait()` 后（`warnIfPrefixOverBudget`，`prefixWarnOnce` 只打一次）与每步 `Loop step request` 日志（新增 `tool_tokens` / `sys_tokens`）都能看到前缀涨没涨。**为什么用单测而不是 eval**：前缀是确定性文本，eval 只能看行为翻转，量不出几百字符的浪费；反过来也不该让 eval 判大小——所以 eval 只把 `prefix_tokens` / `tool_count` 当指标记录（见 `doc/admAgent-eval-harness-plan.md`）。**caps 按 128k 分档**：`deriveSummaryMaxTokens` 3072→6144、`deriveToolResultMaxTokens` 2000→3000（低于 128k 逐字节保持旧行为），给大窗口更多"留在上下文里的事实"（不依赖模型主动 recall 的准确性）；`deriveToolResultCompressThreshold` 保持 6% 但**下限 2000、上限 12000**（`toolResultCompressThresholdCap`）——下限确保高于 `recallToolTokenBudget`（召回结果不被二次压缩），上限防止 6% 在大窗口上失守（1M 窗口下 6% = 60k，实测一条 25.6k token 的 fetch 结果原样进了上下文）。**分档点是 128000 而不是 128KiB（131072）**：厂商标称 128k 的模型配的就是 128000，写 131072 会把最常见的 128k 窗口恰好排除在小档（实测日志 cw=128000 → guard 89600 仍走 3072 小档，也不打 shortfall 警告）。
- **系统提示词的分段与去重原则（`admAgent/internal/agent/templates/coder.md.tpl`）**：静态段只有 7 个（`critical_rules` / `communication_style` / `workflow` / `decision_making` / `intent_clarification` / `editing_files` / `code_conventions` / `tool_usage`），之后才是注入段（`env` → `project_structure` → `lsp` → `available_skills` + `skills_usage` → `project_context` → `user_preferences`）。原则：**机械细节只写在工具描述里，系统提示只放跨工具约束**——edit/multiedit 的白空格与匹配规则、bash 的 background/`description` 规则、grep/glob/view 的"何时用/何时别用"都在各自的 `.md` 里，系统提示只保留一次引用；同一条规则不允许在两处出现（旧模板里 `<bash_commands>` 教"用 `&` 起后台"，bash 工具描述却写 "NEVER use `&`"，模型收到的是互相矛盾的指令）。`agent`/`agentic_fetch` 子 agent 用 `task.md.tpl`，只有一条精简的搜索型提示，不要往里堆 coder 的规则。技能激活流程只在（`{{if .AvailSkillXML}}` 包住的）`<skills_usage>` 里写一遍，`critical_rules` 第 12 条只留一句指针——同一套流程写两处迟早漂移。2026-11 精简结果：模板 28,953 B / 7,253 tok → 11,880 B / 2,976 tok（-59%），本仓库整包（系统提示 + 27 工具 schema）19.0k → 14.1k tok。
- **工作流剧本属于 skill，不属于工具描述**：bash 描述里曾内联 `<git_message_quality>` / `<commit_messages>` / `<git_commits>` / `<pull_requests>` 四段共 5.2k 字符（占该工具描述的 67%），而它们只在用户要求提交/建 PR 时才用得上，却随每一次请求计费，且与内建 skill `git-commit` 大面积重复。现在这四段搬进 `internal/skills/builtin/git-commit/SKILL.md`（提交信息规范、HEREDOC 用法、hook 失败处理、`git show --stat` 验证、列表报告、PR 全流程），bash 描述只留 `<git>`：一句「先 `view` 该 skill」+ 硬禁区（不 push、不改 config、无 `-i`、无空提交、rebase 一律 `-m`）+ **无法静态化的动态署名 trailer**（`attribution.trailer_style` / `model_id` 由模板按配置渲染，skill 是纯 markdown 做不到）。`coder.md.tpl` 的 `critical_rules` 第 5 条同步改成指针。**判断新增内容该放哪里的标准**：只在少数轮次用到的流程 → skill；每次请求都必须遵守的机械约束 → 工具描述。
- **`<project_structure>` 按深度预算注入**（`internal/agent/prompt/prompt.go`）：`fsext.BuildProjectTree(workingDir, depth, 200)` 的 depth 由 `options.project_tree_depth` 决定（默认 2，夹在 1–8；`0` 取默认）——旧值 depth 4 / 600 文件会把整棵仓库树塞进每一次请求。默认收浅的代价是深层文件要多花 1–2 步 `ls`/`glob`/`grep`，收益是常数级前缀成本不随仓库变大。回归：`TestCoderPromptContainsProjectTree`（默认深度必须看不到 `internal/x/foo.go`，`project_tree_depth=4` 时必须看得到）。
- **提示词缓存（provider prompt cache）靠"稳定前缀"而不是显式开关**：wire 只有 OpenAI 兼容的 `/chat/completions`（`internal/llm/wire.go`），没有 Anthropic 式 `cache_control` 断点，缓存命中完全取决于**请求字节的最长公共前缀**。因此三条不变式必须守住：① 系统提示词每个 coordinator（工作区）**只构建一次**（`coordinator.buildAgent` 的 `readyWg`），不随轮次重算——`<env>` 里的 git status 与文件树按"会话开始快照"语义即可；② 工具目录一次性构建并按名称排序（`buildTools`），每步复用 `llmtools`；③ 每步易变内容只往**尾部**加（Rail 3 召回块、nudges、fold 的排队消息），绝不回写历史或 system；④ `preparePrompt`（`internal/agent/agent.go`）塞在请求首位的 todo 系统提醒必须**字节稳定**——它占第 0 个消息位，任何按轮变化（旧文案断言 “your todo list is currently empty”，建表后即为假）都会让整段历史的前缀缓存失效，实时进度只走尾部 `todoProgressReminder`。回归守卫：`TestAgentLoopRequestPrefixIsStable`（`internal/agent/llm_cache_prefix_test.go`）断言同一轮各步的 system 文本、工具摘要逐字节相同，且上一请求的每条消息在新请求里位置与内容不变。日志：`Loop step request` 带 `prefix_sha`（工具目录 + system 的摘要，同轮内应恒定；变了就是缓存被打断）与 `tool_tokens` / `sys_tokens`（前缀的两半，涨了能一眼看出是哪一半涨的），`Loop step response` 带 `cache_read_tokens` / `cache_hit_pct`。计量映射：`internal/llm` 把 DeepSeek 的 `prompt_cache_hit_tokens` 与 OpenAI 的 `prompt_tokens_details.cached_tokens` 都映射到 `Usage.CachedTokens`，循环里换算成 `Usage{CacheReadTokens: cached, InputTokens: prompt−cached}`——这样 `ContextTokens = InputTokens + CacheReadTokens` 仍等于 provider 报的 `prompt_tokens`，而成本按未命中/命中分别计价。之前只解析 `prompt_tokens`，缓存命中率永远是 0，缓存失效（前缀被改写）在日志与账单上都看不出来。回归：`TestStream_PromptCacheAccounting`。低于该线时 `Summarize` 会打 `context window leaves a small work window` 警告（带 work_window_tokens/fixed_overhead/advice），提示改窗口或精简工具目录/系统提示。**caps 按 128k 分档**：`deriveSummaryMaxTokens` 3072→6144、`deriveToolResultMaxTokens` 2000→3000（低于 128k 逐字节保持旧行为），给大窗口更多"留在上下文里的事实"（不依赖模型主动 recall 的准确性）；`deriveToolResultCompressThreshold` 保持 6% 但**下限 2000、上限 12000**（`toolResultCompressThresholdCap`）——下限确保高于 `recallToolTokenBudget`（召回结果不被二次压缩），上限防止 6% 在大窗口上失守（1M 窗口下 6% = 60k，实测一条 25.6k token 的 fetch 结果原样进了上下文）。**分档点是 128000 而不是 128KiB（131072）**：厂商标称 128k 的模型配的就是 128000，写 131072 会把最常见的 128k 窗口恰好排除在小档（实测日志 cw=128000 → guard 89600 仍走 3072 小档，也不打 shortfall 警告）。
- **压缩节奏三原则（本地模型实测驱动，改这几处前先读 `doc/admAgent-fact-block-and-recall-refs-plan.md` §7）**：① `maxSummarizeResumes` 是**连续无进展**上限（`nextSummarizeResume`：跑满 `compactionProgressSteps`(3) 步才撞 guard = 有进展 → 计数重置为 1），长任务可以压缩任意多次，熔断时返回明确错误而不是空 error 静默收尾；② 压缩目标水位是 guard 用量的 `compactionHeadroomRatio`(0.85)（`compactionTargetBudget`，clamp 与 tail budget 同步），**且尾部预算自己也要留工作窗口**（`recentTailBudget` 用 `reservedWorkWindow = min(25k, usable/2)` 封顶）——否则尾部能长到落点贴着 guard：实测日志保留尾部 1.9k→4.7k→7.2k→16.6k、落地水位 19k→22k→27k→36k、间隔 18m→14m；③ 超大工具输出**必须在入口就被压掉**（阈值 6% 且上限 12k + `truncateToolOutputDeterministically` 兜底），否则单步 +12k token 会吃掉整个工作窗口。
- **Rail 3 归档投影（服务端 `internal/context/archive_text.go`）**：归档条目不再是 `msg.Content().Text`。工具消息的正文只存在于 `ToolResult` part、工具调用参数只存在于 `ToolCall.Input`，旧实现两者都拿不到，于是**工具输出与 edit/view/grep 细节从未进过 rail3.db**（`recall` 只能召回叙述文本；`#N` 区间因此大量空洞）。现在 `ArchiveText` 按角色投影：Tool → `[tool result <name> (error)]` + 正文（二进制只留占位说明）；Assistant → 正文 + `[tool call <name>] <单行化后的参数>`（每调用 1200 token 上限）；User → 原样。整条上限 `maxArchiveEntryTokens`=4000，超出追加 `[archived entry truncated…]`（全文仍在 `admAgent.db`）。摘要消息仍由 `CompactWithBudget` 单独处理（剥 anchor/facts 后归档），`ArchiveText` 对摘要返回空。**新增归档来源时必须复用这个投影**，否则又会出现"某些 part 永远不可召回"。`clampContextUnderLimit` 丢弃保留尾部的旧消息前也先走 `Manager.ArchiveOriginal`（`Turn=-1`），避免"被 clamp 掉 = 永久丢失"。
- **统一 token 估算器（`internal/tokencount`）**：压缩预算与发送守卫必须用同一套估算，否则会出现"预算说没超、provider 说超"。规则：ASCII 字节 /4（与旧行为逐字节一致），**非 ASCII rune 计 1 token**（中文实测 ≈1–1.5 token/字；旧的 `context.approxTokens` 用 rune/4、`AnchorStore.CompactToBudget` 用字节/4，把中文预算放宽了 3–4 倍）。接入点：`agent.approxTokenCount`、`context.approxTokens`、`truncateRunesToTokens`、`truncateToTokens*`、`clipMiddleToTokens`、`AnchorStore.CompactToBudget`。另新增 `messageTokenCount`（正文 + reasoning + **全部 ToolResult 正文** + **ToolCall.Input** + 内联文本附件）替换所有"只数 Content().Text"的预算点（尾部预算、压缩前后计数、clamp 扣减、摘要档位比例）——旧算法看不到工具结果/工具参数/文本附件，保留尾部可以远超预算而守卫以为还有空间。
- **超大保留消息定点截断（`truncateOversizedKeptMessages`，`agent.go`）**：压缩后若仍高于落点水位（`compactionTargetBudget`），先找出**单条**超过 `outlierMessageTokens = max(落点/4, 2×工具结果上限)` 的保留消息，对正文/推理/工具结果做确定性截断（`clipMiddleToTokens` / `truncateToolOutputDeterministically`），截断前把原文写进 Rail 3（`Manager.ArchiveOriginal`，`Turn=-1`、不可 `#N` 寻址但可 `query`），然后 `messages.Update` 落库并重算 token。它替代"对一个超大输出再跑两档 LLM 压缩"：摘要替换的是旧历史，而这条消息在保留尾部，重压一次也不会变小。命中时打 `Agent: truncated an oversized message kept verbatim instead of re-compacting`（带 before/after/threshold/target）。摘要消息、user 消息（含任务目标）永不重写；一旦落到目标水位即停止。
- **压缩冷却的跳过语义（`errSummarizeSkipped`）**：`Summarize` 在 30s 冷却内不再返回 `nil`，而是返回哨兵错误；`Run` 识别后等完剩余冷却（`waitSummarizeCooldown`，最多一个窗口、可取消）再重排队，并且**不消耗** `maxSummarizeResumes` 配额——旧行为会把"一次都没压"当成"压缩无效"，4 次后以 `context compaction is no longer buying usable work time` 结束本轮。手动 `/summarize` 在 `coordinator.Summarize` 把该哨兵映射为成功（冷却期内重复点击是 no-op，不报 500）。日志：`summarize skipped, a compaction just ran for this session`（带 remaining）与 `waiting out the summarize cooldown before retrying compaction`。

- **`view` 读图片（`admAgent/internal/agent/tools/view.go`）**：图片文件（PNG/JPEG/GIF/WebP/BMP，上限 `vision.MaxImageBytes`=20MB）不再被拒绝。按**主模型能力分流**（`coordinator.supportsImageViewing` → `NewViewTool` 的 `supportsImages` 参数）：`supports_images=true` 时返回 `image` 类型工具结果（`Data`+`MediaType`+一句文本，文本不能省——空 content 的 tool 消息会被严格上游拒绝）；纯文本主模型改走 vision bridge（`visionDescriber` 包装 `vision.Describe`，尊重 `agent_vision_model`）返回文字描述，避免图片 part 把会话打废。**图片必须额外搬运一次才能到模型**：OpenAI 兼容协议的工具结果只能放文本，所以 ① 当轮 `agent_loop_llm.go` 用 `toolResultWireMessages` 在 tool 消息后追加一条带 `image_url` 的 user 消息；② 后续轮次 `fantasyMessagesToLLM(history, supportsImages)` 把 tool 结果里 base64 的 media 重新搬成同样的 user 消息（同一段连续 tool 结果只产出一条，保持 tool 相邻、不破坏 tool_call 配对）。旧的无调用方的 `workaroundProviderMediaLimitations` 已删除。`agentic_fetch` 子 agent 用同一套 describer；摘要（`Summarize`）调用传 `supportsImages=false`，图片不进摘要请求。PDF 等其它二进制仍在非 UTF-8 分支被拒绝（只能前端转图后当附件发）。回归测试：`internal/agent/tool_media_wire_test.go`（转换层）+ `tool_image_loop_test.go`（mock provider 跑完整一轮，断言第二次请求体里出现 `image_url` 与 `data:image/png;base64,`）；真机形状验证脚本 `tmp/live_image_check`（`go run ./tmp/live_image_check [模型]`，用 admAgent.json 里的 provider 直连，2026-10-31 实测 `deepseek-v4.1-flash` / `glm-5.3-flash` 对"tool 消息 + 带图 user 消息"均正常返回图像颜色）。

## 工具与权限边界

- **撤销数据清理只认单段会话 ID**（`internal/undo/snapshot.go` 的 `PurgeSession`）：`sessionID` 来自 `DELETE /v1/workspaces/{id}/sessions/{sid}` 的路径段，Go 1.22 的 mux 会把 `%2F`/`%2e%2e` 解码出来。命名空间是 `path.Join(refs/admAgent/undo, sessionID)`，`sessionID="../../heads"` 会被清理成 `refs/heads`，随后 `for-each-ref` + `update-ref -d` 把本地分支全删掉。现在入口用 `isSingleRefComponent` 拦住非单段值（空串、`.`、`..`、含 `/` 或 `\`）并打 `Undo purge skipped: invalid session id`。**新增任何"用 sessionID 拼 git ref / 拼路径"的入口都要过同一道校验**；附件目录那边用的是 `safeSessionComponent`，别各自发明。
- **bash 只读自动放行列表的边界**（`internal/agent/tools/safe.go`）：`safeCommands` 只放"无文件/进程/仓库副作用"的程序，`kill`/`killall` 曾误列其中，导致 `kill -9 <pid>` 不弹权限提示就能终止用户的编辑器/测试进程，现已移除。标为只读的 git 子命令（`diff`/`log`/`show`/`grep`/`rev-parse` …）也不再无条件放行：`--output`、`-O<cmd>`、`--open-files-in-pager`、`--ext-diff`、`--exec-path` 会把只读子命令变成写文件或执行命令（`git diff --output=/path`），一律降级为需要授权。回归测试 `TestIsSafeGitCommandRejectsWriterAndExecFlags`、`TestSafeCommandsExcludeProcessTermination`。
- **工作区内 edit/multiedit 免提示的包含性判断**（`internal/permission/permission.go`）：自动批准依赖 `filepath.Rel(workingDir, dir)`，父目录恰好返回 `".."`——它不以 `".."+分隔符` 开头，早期写法会把它当成"工作区内"直接放行，等于把沙箱边界放宽一层。现在显式排除 `rel == ".."`。回归测试 `TestPermissionService_EditAutoApproveStaysInsideWorkingDir`。
- **越界读取判定按真实路径**（`internal/agent/tools/view.go` 的 `resolveForContainment`）：`filepath.Abs` 不解析符号链接，工作区内一个指向 `~/.ssh/id_rsa` 的链接在词法上是子路径，读它不会触发越界权限请求。现在比较前对目标（不存在时回退父目录）和工作区都做 `EvalSymlinks`。新增任何"路径是否在工作区内"的判断都按这个标准，别回到纯词法比较。
- **edit/multiedit 的漂移匹配必须拒绝多义**（`internal/agent/tools/edit.go` 的 `uniqueMatch`）：空白容错/fuzzy/ngram 分支返回的是"匹配到的原文块"，不返回位置，调用方再用 `strings.Index` 重新定位——块在文件更早处也逐字出现时就会改错区域且报成功。现在这三条分支命中后先确认该块在文内唯一，否则返回 `matchAmbiguous` 让模型补上下文。
- **写文件后通知 LSP 用解析后的绝对路径**：`write` 曾把未解析的 `params.FilePath` 传给 `notifyLSPs`，而 `lsp.Client.HandlesFile` 要求工作区绝对路径前缀，相对路径被判 false → 不发 `didChange`，紧随其后的 `getDiagnostics` 返回写之前的诊断。`edit` 早就是把 `params.FilePath` 回写成 `SmartJoin` 结果，`write` 现已改传局部变量 `filePath`。

## 网络代理链路

- **网络代理链路**（设置→网络代理，仅影响 admAgent，桌面端下载不走代理）：
  1. 前端 `settings.js` `saveProxy()` 校验（启用时 url 必填、须以 `http(s)://` 或 `socks5://` 开头）→ `save_settings` 写入 config.json 的 `agent_proxy`。
  2. Rust `settings.rs:37` 调用 `agent.rs` `sync_agent_proxy`：`write_agent_proxy`（`agent.rs:640`）把 `{enabled,url}` 写入 admAgent.json 顶层 `agent_proxy`（原子写，值未变返回 false 跳过）→ 有变更时对当前 active workspace `POST /v1/workspaces/{ws}/config/set` 触发服务端**磁盘全量重载**（10s 超时，失败仅记日志退回直连）。
  3. admAgent `ConfigStore.setConfig` 把代理同步到进程级 `httpproxy`（`internal/config/store.go:100-105`）；`httpproxy.ProxyFunc()` 作为 `Transport.Proxy` 回调**每次请求实时读取**状态，热重载即刻生效、无需重建 client/重启 server；本地/私网地址（127.0.0.1、LAN GPU 盒）自动绕过（`internal/httpproxy/proxy.go:50-81`）。
  4. **生效范围**：LLM 客户端（`llm/client.go:107`）+ Agent 网络工具 fetch/web_fetch/download/web_search/sourcegraph/agentic_fetch（全部经 `SharedHTTPTransport`，`tools/fetch_helpers.go:38-48`）；**MCP HTTP/SSE 传输不走**（`mcp/init.go:538-581` 用 `http.DefaultTransport`，只认 `HTTP_PROXY` 环境变量）。注意：面板文案"仅影响 LLM 请求"比实际范围窄，工具类请求同样走代理。
