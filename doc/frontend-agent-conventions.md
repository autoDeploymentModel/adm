# Agent 视图前端约定（桌面端）

> 范围：`src/views/agent/` 的错误处理、自动续跑、假完成检测、拖拽选择保护、工作目录切换与消息按轮懒渲染，以及同目录多会话并行的前台状态模型。

---

## 结构化日志（Agent 视图）

- 所有前端日志走 `views/agent/log.js`，不再直接 invoke 旧 `agent_debug_log`。新接口为 `log.debug/info/warn/error(comp, evt, msg, attrs, trace)`；旧两参数调用仍兼容，但新代码必须写精确事件名。
- logger 自动带 `origin=ui/doc/ui_seq/ts_ms`，100ms/50 条批量；WARN/ERROR 立即发送。`pagehide` 与隐藏页面时 best-effort flush。`Settings.debug_logging` 关闭时仍保留 WARN/ERROR。
- trace 只使用契约键，发送动作带 `ws/session/run`，SSE 带 `ws/session/run/type/bytes`；不得把 prompt、工具入参、命令、响应正文塞进 attrs。
- `window.onerror`、`unhandledrejection`、`reportError` 与 `ui.js reportError` 统一写 `ui.error`；message/stack 脱敏后可见，stack 上限 32KB。
- `store.js` 的 `_log` 只是统一 logger 的薄封装；不要恢复内联 IPC 日志，否则会绕过批量、级别与脱敏。

## 前端错误处理（Agent 视图，`src/views/agent/`）

- **统一提取**：所有服务端错误（API invoke 抛错、SSE 事件内嵌 error）先用 `error.js` 的 `getErrorMessage()` 提取可读文本（兼容 string / Error / `{"error":{"message","type"}}` / 其它对象），再用 `classifyError()` 分类（quota/timeout/network/not_found/cancel/unknown）。
- **统一展示入口**：错误统一走 `ui.js` 的 `reportError(err, { prefix, hint })`，内部自动提取+分类：quota（401/余额/授权）类直接显示"余额不足，任务中断"，其余显示原始错误；三档 UI 为 `showNotice(msg, level)`（error 红 / warn 黄 / info 灰），消息区节点 3s 自动消失，`showError/showWarning/showInfo` 是薄封装。
- **禁止** `showError("前缀: " + e)` 直接拼接错误对象（对象会显示 `[object Object]`）；应把**原始错误**传给 `reportError(e, { prefix })`。本地状态提示（无服务端错误对象，如"文件过大"、轮数上限）才直接用 `showError/showWarning` 字符串。
- **SSE 错误路径**：`run_complete` / `agent_event` 内嵌 error 均走 `reportError`，不要在 sse.js 里自行实现 formatRunError/isQuotaError（已在统一模块）。
- **模型不支持关闭思考**（`error.js` 的 `ERROR_THINKING_UNSUPPORTED`）：provider 同时拒绝 `reasoning_effort:none` 与 `thinking.disabled` 时，admAgent 返回 400，文案以 **`thinking_mode_unsupported`** 开头（前后端契约 token，`internal/llm/client.go` 产出、`client_test.go` 锁定，改文案须保留）。桌面端按该 token 分类（早于 network 匹配——被包裹的 provider 原文含 "Upstream request failed"），提示"本模型不支持关闭思考，请切回思考模式"并**中断本轮**；既不自动恢复默认档，也不静默去掉参数继续跑。注意服务端现在还会在「GGUF 模板只接受自己的推理档位词表」时复用该 token（如只认 xhigh/medium/low 的模板收到 none），语义一致。
- **本地推理引擎故障的两类错误**（`error.js` 的 `ERROR_ENGINE_CRASH` / `ERROR_ENGINE_DOWN`，必须早于 `NETWORK_RE`）：① `engine_crash` 命中 llama.cpp 的 `decode() failed: vk::Device::waitForFences: ErrorDeviceLost`（GPU 驱动重置/显存压力，进程随后退出），提示"推理引擎因显卡驱动重置退出，任务中断。请重新启动模型；若反复出现请降低上下文大小或只选独立显卡"；② `engine_down` 命中本地地址（127.0.0.1/localhost/::1）+ `connection refused/connectex`，即引擎进程已不在（崩溃未重启/被手动关闭），提示到「模型列表」重新启动后再发送。这两类以前都落进 network/unknown，只显示"连接失败/操作失败"，用户不知道是模型进程死了（2026-11 日志：DeviceLost 后两次「继续」都是裸 connection refused）。崩溃事件的全局提示与运行状态同步在壳层，见 [`frontend-architecture.md`](frontend-architecture.md)。
- **假完成/静默停止检测**（`sse.js` `detectFakeCompletion`）：本轮有 edit/write/multiedit/bash/lsp 等副作用工具调用、但工具调用总数 ≤4、且 prompt 含操作动词（部署/修复/重构…）时，`showWarning` 提示"任务可能未完整执行"（服务端重试耗尽后 run_complete 无 error 静默结束的兜底）。
- **任务清单未完成提示**（`sse.js` run_complete 收尾）：`action.kind === "ok"` 且 `run_complete.incomplete_todos > 0` 时弹常驻 `showNotice(..., "warn", true)`「任务清单还有 N 项未完成，本轮已结束；可发送"继续"让模型收尾」。`todos` 面板按会话快照渲染（`renderTodos`），服务端未回写完成态时面板就是 0/N——这类"终稿说做完了、清单还全没勾"的矛盾必须靠该提示暴露，不要在前端按终稿正文自动把清单改成完成。清单是会话累积的，旧清单未清掉时后续每轮都会再次触发，提示节点用 `todosNoticeEl` 复用改写文案（节点被 `clearErrorNotices` 清掉后自动重建），否则每轮会叠一条相同黄条。
- **自动续跑进度判定**（`autocontinue.js` `maybeAutoContinue(data, runStats)`）：本轮有 edit/write/bash 等实质副作用工具**成功落地**（`runStats.sideEffectSuccess > 0`）视为有进展、不计无进展，避免"模型在干活但没标 todos"被误熔断。
- **工具卡状态跟随结果**（`render.js` 的 `toolStatusSuffix`）：`is_error` 的 tool_result 到达后摘要显示「(失败)」并标红，而不是「(已完成)」。旧版只看 `finished`，于是被 `stale_read` 守卫拒绝的编辑卡片写着"已完成"、正文却是红色错误，用户只能自己判断哪一半是真的。

## 运行态交互约定

- **切换工作目录的体验与性能约定**（`workspace.js` 的 `switchToWorkspace` / `doSwitchWorkDir` / `refreshProvidersOnSwitch`）：
  - **先反馈、后联网**：判定首访 → `store.setActive` → 立刻 `updateWorkspaceSelector()` + `updateDecisionModeUI()` + 状态栏 + `updateSendButton()`，然后才发网络请求。旧实现把这些放到最后一个 `await` 之后，点击后界面长时间毫无变化，这是"卡顿感"的主要来源。
  - **冷启动（首次进入该 workspace）只串行一个必须的请求**：`POST /agent/init`（服务端此刻才真正构建 coordinator，见 `doc/admAgent-server.md`）→ `Promise.all([syncModeToServer, enableAutoCompact, GET /agent])` → `await loadConversations()`（首屏主体，内部会自动打开上次会话并按页加载其消息；聊天区每轮默认折叠，只显示轮标题）。`loadTools()` 与 `refreshProvidersOnSwitch()` 改为 fire-and-forget，不再阻塞切换。
  - **热切换（切回已访问的工作区）0 次写盘、0 次串行等待**：恢复快照 + 全量重绘后立即返回；`loadConversations` / `refreshAgentInfo` / `loadTools` / provider 刷新全部后台跑。切换期间用 `showInitProgress`/`hideInitProgress` 给一条明确的进行中提示（`doSwitchWorkDir` 在建工作区阶段就显示，`switchToWorkspace` 冷路径 `finally` 收起）。
  - **不要再用 `config/set` 制造 reload 副作用**：`refreshProvidersOnSwitch` 改用只读的 `POST /v1/workspaces/{id}/config/reload`（只重读配置，不写文件）；仅在旧版 sidecar 不认该端点时报错回退到旧的"回写同一 api_key"路径。`enableAutoCompact` 在内存里按 workspace 记住已开启，服务端 `SetCompactMode` 对同值也跳过写盘。
  - **保留的既有约定**：末尾必须重算 `updateSendButton()`（工具栏显隐）与 `syncConvTitle()`（标题栏），`reconcilePdfBatching()` / `syncWxFollowSession()` 在切换后各跑一次；这些顺序不要被新的并行化打乱。
- **同目录多会话并行**（桌面端，`agent_concurrent_sessions` **默认关**，需在 Agent 设置→基础设置里手动开启；并发上限 3）：服务端运行态本就按会话隔离（`activeRequests`/`messageQueue`/`cancelMark`/`sessionMu` 均以 sessionID 为键），并行无需服务端改动，由桌面端状态模型与开关控制。`store.js` 按会话登记运行：`runs`（sessionId→活动运行）、`queued`（sessionId→排队轮次数组，FIFO）；`S.activeRun`/`S.queuedRun`/`S.runStats` 是 `currentConvId` 的**派生视图**（沿用旧语义=「当前打开会话的运行」），`S.isSending`=「本工作区有任一运行在飞」，`S.runs` 供会话列表/状态栏标识（workspace 状态池快照会带上 `runs`，切回工作区即恢复）。`run_complete` 只注销发起它的会话（`store.handleSSEEvent` → `completeRun(wsId, sessionId, runId)`，run_id 不匹配= 迟到的旧事件直接丢弃，避免误清新一轮），非当前会话的完成只刷新列表（`sse.js` 用处理前快照 `ctx.prevRuns` 判定归属）。开关与上限在**附件/PDF 转换之前**判定（否则已转换的 PDF 批次会被静默丢弃）；关闭时其它会话运行期间拒绝新会话发送（旧的"跨会话排队"是客户端假象——服务端早就并发跑了）；同会话内不可折叠的轮次（决策轮/分批发送）仍登记为 `queued`。写冲突护栏：`edit`/`write` 的读后写守卫跨会话天然生效（mtime > 本会话 lastRead 即要求重读），撤销入口在并行运行期间被前端拦下（服务端 undo 是整仓库回滚）。服务端侧防护已落地（admAgent：`SessionAgent.ActiveSessionIDs` + `coordinator.Undo` 并发拒绝、`internal/agent/tools/filelock.go` 按路径写锁、`filetracker.RecordWrite/LastWriteBy` + 写前跨会话提示），详见 `doc/admAgent-parallel-sessions-file-guards.md`；admAgent 改动需重编译推送 sidecar 才在 ADM 生效。
- **工具栏显隐必须随工作区切换重算**（`workspace.js` `switchToWorkspace` 在恢复/清空状态后立即调 `updateSendButton()`，两条分支都不例外）：后台 workspace 的 `run_complete` 只更新状态池、不走 UI 副作用（`sse.js` 按 active workspace 过滤），而「停止」按钮的显隐只由 `updateSendButton()` 维护。切换时不重算会沿用上一个工作区的按钮状态——任务早已结束「停止」仍常驻（点它 `cancelCurrentRun` 因 `activeRun` 为空直接返回，无副作用但误导），或切进正在运行的工作区却看不到停止按钮。
- **标题栏（`.chat-header` 的 `#agent-conv-title`）也必须随工作区切换重算**：`store.setActive` 只把目标 workspace 的 `currentConv` 恢复到状态池、不碰 DOM，切回已访问过的工作目录时标题栏会残留上一个工作区的会话名，与下方消息区（`renderMessages` 已按恢复的会话重绘）自相矛盾。`switchToWorkspace` 的非首次进入分支用 `syncConvTitle()` 按恢复后的 `currentConvId` 重写标题（会话列表里同 id 的项优先，服务器标题更新后以列表为准），并在 `loadConversations()` 之后再同步一次。**占位文案只在没有可打开的会话时写**：`syncConvTitle` 在 `currentConvId` 为空时，仅当本地会话列表也为空才写「选择或创建一个会话」——热切换到零会话工作区时标题栏不得残留上一个工作区的会话名；列表非空则不动 DOM，由 `loadConversations` 自动打开上次会话并写真实标题，重算逻辑不得抢先覆盖。
- **底部状态栏的工具调用 / 交互轮次统计**（`template.js` 的 `.agent-status-bar` + `ui.js` 的 `updateSessionStats`）：Token 一段沿用 `S.contextUsage`（服务端 `context_tokens`；为 0 时回退本地估算并加 `~`），右侧两段计数**完全由前端按 `S.messages` 现算**，不新增服务端字段。口径：工具调用 = `tool_call` part 数（`shell_command` 是用户 `!` 命令、`decision` 是决策结果 part，均不计）；交互轮次 = assistant 消息数（服务端每个 step 落库一条 assistant 消息，含压缩摘要消息，一步即一次模型请求）。刷新绑在 `renderMessages` 末尾（含空消息分支）：流式期间经 rAF 合并渲染自然增量刷新；**不要**改成只在 `run_complete`/`session updated` 时计算，否则一轮跑完前数字一直不动。消息一次全量加载（见下方「消息整表加载」），两项计数与本地 token 估算基于完整历史。
- **上下文用量的 max 只认服务端 `ctx_size`（旧键兜底）**：`S.contextUsage.max` 的刷新入口（初始化、`refreshAgentInfo`、`switchToWorkspace` 恢复）都读 `/agent.model` 的窗口，必须走 `utils.js` 的 `modelContextWindow`（`ctx_size` 优先、`context_window` 仅旧版 admAgent.json 读入的模型才有）；直接读 `context_window` 会让内存构造的内置模型（`admAgent/adm-models`）窗口读成 0，选择后顶部用量继续沿用上一个模型的 max。细节见 [agent-settings.md](agent-settings.md)。
- **会话列表分页 + 消息按轮懒渲染**（`session.js` / `render.js`，长会话/多会话工作区的加载性能约定）：
  - **会话列表**：`loadConversations()` 只拉第一页（`GET /sessions?limit=100`，`updated_at DESC`），`store.convsComplete` 记录是否到底；列表尾部挂「加载更多会话…」哨兵（`.conv-load-more`），点击或滚动接近底部（60px）触发 `loadMoreConversations()` 按 `offset` 补拉，`appendConversations` 按 id 去重（新建会话插顶会使偏移漂移，去重兜底）。「清除全部」会先逐页补拉到底拿到完整 id 清单再删，不会漏掉未加载页。**无进展保护**：某页按 id 去重后无新增（旧版 sidecar 忽略 `limit`/`offset`、或并发增删导致分页漂移）即判定无法前进、按已加载清单收尾，`appendConversations` 会强制把 `convsComplete` 置 true，避免同一请求无限重发（「清除全部」的补拉循环尤其必须依赖这条）。
  - **默认打开上次会话（不新建空会话）+ 加载中占位**：`loadConversations()` 在 `currentConvId` 为空且列表非空时自动打开列表首项（`updated_at DESC`，即上次会话），聊天区按轮渲染——每轮默认折叠只显示标题条，点击标题再展开正文；左侧「对话记录」照常展示全部会话标题，点击其它标题切换到对应会话内容。**不再自动创建空会话**（旧实现会在切换工作目录后凭空多出一条「新会话」）；发送时若仍没有当前会话，由 `send.js` 自动新建。列表从未完成过一次加载（首访工作区 / 切换后请求返回前，含工作区初始化阶段还没发出 `/sessions` 请求的空档）且列表为空时显示「加载中...」（`.conv-list-loading` + `.conv-list-spinner`），**不能显示「暂无会话」**（否则用户会把加载中误读成该目录没有对话）；`session.js` 的 `convListLoadedOnce` 按 wsId 记录是否已加载过，加载结束（成功或最终失败）后空列表才允许显示「暂无会话」。分页补拉期间列表尾部哨兵文案切换为「加载中...」，失败时恢复「加载更多会话…」。
  - **消息整表加载（不分页）**：`selectConversation` 直接 `GET .../messages` 拉全量历史，聊天区按轮列出**全部**轮标题（每轮默认折叠，只建标题条、不建消息 DOM，整表加载的渲染代价可控）；**不要**恢复「只拉最近一页 + 顶部『加载更早的消息』补拉」的分页方案——那会让切换后的轮清单残缺（只看到最近几十条消息覆盖的几轮），用户无法「默认看到所有轮标题」。**会话归属守卫**：`selectConversation` 在每个 `await` 之后（含 catch 的清理分支）都比对 `S.currentConvId` 与发起时的 workspace id，切走即丢弃结果——store 的 `messages` 随选中会话整体替换，迟到响应会污染新会话列表，迟到的 404 还会把当前会话改选到别的会话。
  - **按轮懒渲染正文**（`render.js` 的 `renderMessages`）：默认只建每轮标题条（`.msg-round-header`，历史轮默认折叠），折叠轮**不建消息 DOM**——渲染循环里只有 `!el.classList.contains("msg-round-collapsed")` 的轮才调 `alignMessagesInContainer`（含决策卡片计算）。展开入口统一走"先置 `_admRoundOpen = true` 再 `renderMessages()`"：header 点击（`buildRoundNode`）、大纲跳转（`session.js` 的 `scrollToRound`）；展开前设 `S.manualScrollMode = true` 保住滚动位置。折叠只隐藏、不销毁已渲染内容，再次展开直接复用。运行中的末轮经 `applyRoundState`（`lastOpenRoundKey`）自动展开以显示流式输出。
  - **`run_complete` 收尾不再整表重拉会话列表**：改 `refreshConversationMeta(sid)` 定向 GET 单会话并就地更新列表项（不在列表则插顶，`updated_at` 变化后重排）。
  - **重新挂载恢复会话（`loadConversations(true)`）不得在本地分页列表上判存在性**：当前会话可能排在第一页之外，误判为已删除会导致静默换会话。直接 `selectConversation(S.currentConvId)`，由服务端 GET 的 404 分支负责清理与回退。
  - **服务端契约**：会话列表不带分页参数时行为与旧版一致（全量），TUI / SDK 不受影响；详见 `doc/server-api.md` 3.1。
- **撤销入口挂在每个对话容器上**（`src/views/agent/undo.js` + `render.js` 的 `buildRoundNode`）：标题栏的那个「撤销上一轮对话」按钮已删除，改为每轮 `.msg-round-header` 右侧一个 `↶`（`.msg-round-undo`）——点它撤销**这一轮及其之后的所有轮次**（跨轮撤销）。服务端 `POST .../undo` 支持可选 `anchor`（该轮起始 user 消息 ID），桌面端**一次调用**带 anchor 完成跨轮回滚；不带 anchor 退回「只回滚最后一轮」（TUI `ctrl+b`）。成功后 `selectConversation` 重拉会话。特殊状态与文案约束：
  - **运行中置灰（不设 `disabled`）**：`S.activeRun`/`S.queuedRun`（本会话在跑或排队）与「同工作区其它会话在跑」都让按钮加 `.msg-round-undo-blocked` 置灰（服务端 undo 是整仓库回滚，会连带回滚别人的改动/提交）；置灰只是视觉提示，点击由 `undoToRound` 重新判定 `undoBlockReason()` 并 `showWarning` 给出原因。**不要改回 `btn.disabled`**：禁用态 `<button>` 收不到指针事件，`title` 不弹、点击也不触发，用户只会看到一个没有解释的死按钮；而且按钮状态只在消息渲染（`applyRoundState`）时重算，运行态在别处变化（如同工作区其它会话结束）时不重渲染，禁用态会一直留着，把入口锁死。**手动取消（停止）后按钮才恢复可用**——这是"发错提示词"的标准修复路径：停止 → 点该轮 `↶`。
  - **跨轮撤销的精度边界**：文件回退依赖服务端保留的**每轮快照**（`options.undo_checkpoints`，默认 10，上限 100；`internal/undo` 的 `DefaultMaxCheckpoints`），快照按整树还原，所以超出保留窗口的更早轮次只能回滚对话记录、文件改动可能残留；确认文案里明确写出这条，不要让用户以为文件一定回退了。多段告警用 `\n\n` 分段（`.permission-body` 已设 `white-space: pre-line`，否则挤成一段）。
  - **非 git 工作目录**：`undo` 的 git 快照只是"回退文件"的手段，没有它服务端会退化为"只删消息"（`coordinator.undoRecord` 合成无 snapshot 的 record，只跑 `cleanupAfterUndo`）。前端用 Rust 命令 `check_git_repo`（`git rev-parse --is-inside-work-tree`，按工作目录缓存）区分「没装 git」与「装了但不是仓库」，在确认弹窗里如实追加提示；两种情况都仍然允许撤销，不因此禁用入口。
  - **禁止**在这里再退回"只回滚最后一轮、前端循环调用"的实现（一次跨轮回滚变成 N 次整树还原，中途失败会停在两轮之间的混合态）；也**禁止**在撤销进行中并发触发第二次（`undoInFlight` 期间全部按钮置灰，点击直接被 `undoBlockReason()` 拦下）。
- **右侧「对话记录」大纲是轮级索引**（`session.js` 的 `renderMessageOutline` + `render.js` 的 `roundOutlineEntries`）：面板每项 = 一个对话容器（`.msg-round`，一条 user 消息为一轮），显示 `#序号 · 时间 · 轮标题`，**不再逐条列 agent 消息**——一轮里几十条工具/思考消息会把面板淹掉，而用户要跳转的粒度是"第几轮在聊什么"。标题复用轮标题条同一份文本（`roundTitleText`：首条 user 消息正文，剔除 `<system_info>` 与决策控制块，无文字时显示"（无文字内容）"），因此面板与容器标题永不打架。点击 → `scrollToRound` 按 `data-roundkey` 定位轮容器、**先展开**（折叠的轮不展开就只看得到标题条）、轮内滚回开头，再给轮容器自身加 `.flash-highlight` 闪烁（`.msg-round.flash-highlight`；消息级 `.msg.flash-highlight` 已随逐条大纲一起移除）。无 user 消息的前导轮（只有本地错误气泡）不进面板；FAB 角标数字 = 轮数，与面板项数一致。
- **前端自动续跑**（`src/views/agent/autocontinue.js`）：本轮正常结束但 todos 未完成时自动发“继续”开新轮（每轮重置服务端 nudge 预算）；上限 10 轮、连续 2 轮无进展自动停；仅续跑本客户端发起的任务；出错、取消、切走会话均不触发；开关存 localStorage（`agent_auto_continue`，默认开）。
- **LSP 工具面板的修复入口由服务端状态驱动**（`lsp_fix.js` + `tools.js`）：能否修复、装什么版本只看 `GET /lsps` / SSE `state_changed` 里的 `fix`/`guide`（不再维护桌面端安装表）；点「修复」→ `POST /v1/lsp/fix`（`confirm=true`，**202 + job body**，Rust `agent_http_request` 对 202 会解析 body 返回——此前一律丢 body 返回 `{}`，前端拿不到 `job_id` 直接报 "missing job_id"，中文界面降级成「修复失败：操作失败，任务中断」，安装其实已在后台跑）→ 每 700ms 轮询 `GET /v1/lsp/jobs/{id}`（120s 超时）→ 按名称 `start` → 轮询状态。job 失败时**直接 `showError` 原始 `error`/`reason` 文本**（npm/pip 输出是排查唯一线索，不走 `reportError`——中文界面会把英文细节整段丢弃只剩「操作失败，任务中断」），并附 `log_tail` 尾部最多 3 行（跳过 `$ npm ...` 命令回显行，单行 ` | ` 拼接，消息区不支持多行）；轮询期间把 `message`+`percent` 刷到「安装/修复」按钮上（`tools.js` 给按钮带 `data-lsp-name`，`lsp_fix.js` 每次按名重查并保持 `disabled`，列表被 SSE 重绘后仍能继续更新；重绘时 `renderToolsList` 用 `isFixInFlight` 把新按钮直接渲染成「修复中…」禁用态，避免进行中按钮看起来可再点）；轮询超时只提示“安装仍在后台进行”，不当作失败（job 可能稍后成功，重试还会撞 409）；LSP 页的「启动失败自动修复」开关与 localStorage `agent_lsp_auto_fix` 已移除，修复只由用户点击触发。`runLspFix` 的 action 取自 catalog 的 `fix.kind`，catalog 一次性缓存后不随安装状态刷新。按钮不再要求 `state==3`：未安装的托管条目（`GetLSPStatesWithManaged` 合并、state=0 + `fix.kind=install_server`）直接显示「安装」按钮（`fixKind==="install_server"` 时文案用「安装」，其余用「修复」）；但 `state=1/2`（启动中/已连接）即使拿到 `install_server` 也不展示「安装」——catalog 兜底与用户自定义 command 都可能让已在运行的服务器残留该 fix，典型症状是 gopls 已连接旁边仍有「安装」。「指引」按钮对 error 态或带 `reason` 的条目显示，但 `state=1/2` 同样不显示（否则用户自定义 command 的已连接服务器会从「安装」换成「指引」）；「AI 安装」仍仅 error 态。
- **拖拽选择保护 / 主线程停顿看门狗**（桌面端）：在消息区按住左键拖拽选择文字期间，`render.js` 的 `beginSelectGuard` 暂停流式 DOM 写入与自动滚底（`renderMessages` 只置待渲染标记、`scrollChatToBottom` 直接返回），抬键（window 捕获 mouseup）/失焦/10s 超时后补渲染一次；消息区 `dragstart` 拦截“从已有文字选区发起的原生拖拽”（图片除外）。原因：WebView2/Chromium 在拖拽选择期间变更 DOM + 程序化 scrollTop 有触发输入卡死的已知回归（crbug 559347435 / 559795247 / 41327805）。`agent.js` 的看门狗每秒采样定时器漂移，>2s 记 `PERF` 调试日志：界面无响应但无停顿记录 = WebView2 输入卡死（上游问题，需更新运行时），有记录 = 前端长任务阻塞。
